## 1. 전송거리에 따른 분류: PAN / LAN / MAN / WAN

**해당 자료: 3페이지, Network Classification by Transmission Distance (Tx-Rx)**

### 핵심 개념

이 페이지의 분류 기준은 송신 측(Tx)과 수신 측(Rx) 사이의 **전송거리** 이다. 그림은 사람 주변 → 집 → 도시 → 지구로 범위가 커지는 순서로 네트워크를 배치한다.

```text
[3페이지 그림의 텍스트 재구성]

PAN                  LAN                 MAN                 WAN
사람과 주변 기기       집 안의 기기         도시의 건물들        지구 규모 연결
1~2 meters           ~100 meter         약 10~50 km         thousands of km
        └────────────── 공간적 범위가 커지는 방향 ──────────────→
```

- **PAN (Personal Area Network)**: 개인 주변의 가까운 기기들이 이루는 네트워크이다. 그림에는 이어폰, 휴대전화, 손목 기기 등이 나타나며 거리는 `1~2 meters`로 표시된다.
- **LAN (Local Area Network)**: 제한된 지역의 기기들을 연결하는 네트워크이다. 그림에는 집 안의 여러 기기가 있고 `~100 meter`로 표시된다.
- **MAN (Metropolitan Area Network)**: 도시 규모의 네트워크이다. 그림에는 도시 건물과 `5G` 표기가 있으며 `약 10~50 km`로 표시된다.
- **WAN (Wide Area Network)**: 넓은 지역을 연결하는 네트워크이다. 그림은 지구와 위성을 사용하며 `수천 km`로 표시한다.

영문 약어의 전체 이름은 용어 이해를 위한 보충 표기이다. 거리 수치는 원자료 그림의 수치를 유지했다.

### 이해용 예시

휴대전화와 몸에 착용한 기기의 연결을 생각한 뒤, 집 안 기기들의 연결, 도시 내 시설들의 연결, 멀리 떨어진 지역 간 연결로 시야를 넓혀 보자. 핵심 질문은 “기기가 몇 대인가?”보다 “어느 정도 공간을 연결하는가?”이다.

### 헷갈리기 쉬운 포인트

- 거리 기준과 유선/무선 기준은 서로 다르다. 3페이지는 거리로 분류하는 페이지이다.
- 도시 그림의 `5G`나 WAN 그림의 위성 하나를 해당 분류의 유일한 기술로 외우지 않는다.
- **보충 설명**: 그림의 거리는 규모를 이해하는 대표값이다. “LAN은 100m를 넘으면 무조건 MAN”처럼 절대 경계로 적용하지 않는다. 실제 연결 범위와 개별 케이블의 전송거리 제한도 같은 개념이 아니다.

## 2. 연결 형태에 따른 분류: Network Topologies

**해당 자료: 4페이지, Network Topologies**

### 핵심 개념

**Topology(토폴로지)** 는 노드와 연결이 어떤 모양으로 배치되는지를 보는 관점이다. 4페이지는 Bus, Ring, Mesh, Star, Tree, Hybrid의 여섯 그림을 제시한다. 아래 설명은 그림의 연결 관계를 언어로 풀어 쓴 것이다.

### 2.1 Bus: 하나의 공통 선로에 연결

```text
[4페이지 Bus 그림의 개념 재구성]
   A      B      C
   |      |      |
===================== 공통 선로
      |      |
      D      E
```

여러 노드가 하나의 공통 선로에 연결된다. 이후 11페이지의 Shared Bus와 12페이지의 Token Bus를 이해하는 출발점이다.

**이해용 예시**: 여러 사람이 하나의 공용 통신선을 함께 사용한다고 생각한다. 누구를 부르는지는 별도로 표시해야 한다.

**헷갈리기 쉬운 포인트**: 버스라는 모양만 보고 CSMA/CD라고 단정하면 안 된다. 물리적 버스를 쓰더라도 토큰으로 전송 순서를 정할 수 있다.

### 2.2 Ring: 이웃을 따라 닫힌 고리 구성

```text
[4페이지 Ring 그림의 개념 재구성]
A ----- B
|       |
D ----- C
```

각 노드가 이웃과 연결되어 닫힌 경로를 이룬다. 이후 Token Ring은 이러한 순환 구조에서 토큰을 돌리는 방식으로 설명된다.

**이해용 예시**: 원형으로 앉은 사람들이 이웃에게 차례표를 전달하는 상황이다.

**헷갈리기 쉬운 포인트**: Ring은 연결 형태이고 Token Ring은 토큰을 이용하는 전송 방식까지 포함한다. 모든 고리 그림을 곧바로 토큰 동작으로 해석하지 않는다.

### 2.3 Mesh: 여러 노드 사이의 다수 연결

```text
[4페이지 Mesh 그림을 단순화한 4노드 예시]
A ----- B
| \   / |
|   X   |
| /   \ |
D ----- C
```

그림은 노드 사이에 많은 연결이 직접 형성된 모습을 보여 준다. 단일 공통 선로나 단일 중심점에만 연결되는 모양과 다르다.

**이해용 예시**: A가 B, C, D와 각각 연결되는 구조를 그려 보면 선의 수가 빠르게 늘어나는 것을 볼 수 있다.

**헷갈리기 쉬운 포인트**: **보충 설명**: Mesh에는 모든 노드 쌍을 연결한 형태와 일부만 연결한 형태가 있다. 연결 경로가 많다는 것만으로 실제 경로 선택 규칙까지 결정되지는 않는다. 이 페이지는 라우팅 알고리즘을 설명하지 않는다.

### 2.4 Star: 중심 장비로 모이는 연결

```text
[4페이지 Star 그림의 개념 재구성]
       A
       |
B -- [중심] -- C
      /  \
     D    E
```

주변 노드들이 중앙의 한 지점에 연결된다.

**이해용 예시**: 여러 PC의 케이블을 중앙 장비에 각각 꽂은 모습을 떠올린다.

**헷갈리기 쉬운 포인트**: 중심이 허브인지 스위치인지에 따라 동작은 다르다. 모양이 별형이라고 충돌 도메인까지 하나로 결정되지는 않는다. 이 차이는 16~17페이지에서 연결해 공부한다.

### 2.5 Tree: 계층적으로 가지가 갈라지는 연결

```text
[4페이지 Tree 그림의 개념 재구성]
        A
       / \
      B   C
     / \   \
    D   E   F
```

상위 노드에서 하위 노드로 가지가 나뉘는 계층 구조이다.

**이해용 예시**: 건물 전체 연결에서 층별 연결로, 다시 각 방의 연결로 갈라지는 모양을 그려 본다. 이는 형태를 이해하기 위한 예시이다.

**헷갈리기 쉬운 포인트**: 여기서 계층은 연결 모양의 위아래 관계이다. OSI 계층 번호와 혼동하지 않는다.

### 2.6 Hybrid: 둘 이상의 형태 결합

```text
[4페이지 Hybrid 그림의 개념 재구성]
[고리 형태의 구간] ---- [가지가 갈라지는 구간]
       Ring                      Tree
```

원자료는 고리와 나무 형태가 결합된 그림을 보여 준다.

**이해용 예시**: 한 구간은 링 형태이고 연결된 다른 구간은 트리 형태인 전체 네트워크를 생각한다.

**헷갈리기 쉬운 포인트**: Hybrid는 특정한 하나의 배치가 아니라 여러 형태를 조합한 구조를 뜻한다.

### 이 절의 연결 질문

3페이지는 “얼마나 멀리 연결하는가?”, 4페이지는 “어떤 모양으로 연결하는가?”를 묻는다. 이후에는 “그 연결 위에서 누구에게 언제 보낼 것인가?”가 필요하다. 그것이 프로토콜과 MAC의 문제로 이어진다.

## 3. Network Protocol과 IEEE 802 LAN 표준

**해당 자료: 5페이지**

### 핵심 개념: 통신에는 물리적 약속과 논리적 약속이 모두 필요하다

원자료는 **Network Protocol** 을 두 측면으로 나눈다.

1. **물리적 측면**: 전송 매체, 접속 단자, 전송 신호 규격 등이다. 실제로 무엇을 통해 어떤 신호를 주고받을 것인지의 약속이다.
2. **논리적 측면**: 데이터 형식(프레임), 주소 지정, 오류 제어, 흐름 제어, 전송 절차 등이다. 전달한 비트들을 어떻게 해석하고 처리할 것인지의 약속이다.

선이 연결되어 있다고 통신 규칙이 완성되는 것은 아니다. 수신자가 데이터의 시작과 끝, 목적지, 오류 처리 방법을 이해할 수 있어야 한다.

### IEEE와 표준 그림 읽기

PDF는 **IEEE (Institute of Electrical and Electronics Engineers, 전기전자공학자협회)** 를 전기·전자·컴퓨터·정보통신 등의 기술 발전을 위한 전문 기술 조직으로 소개하고, 이어서 **IEEE 802 LAN 표준안** 을 제시한다.

```text
[5페이지 IEEE 802 그림의 표기·배치를 텍스트로 재구성]

OSI 관점                         IEEE 802 그림의 구성
데이터링크 계층                   802.2 Logical Link Control | IEEE 802.2
                                 802.1 Mac Bridging | IEEE 802.1d

                                 802.3       802.4      802.5      802.11
                                 CSMA/CD     Token      Token      Wireless
                                 | Ethernet  Bus        Ring       LAN
물리 계층                        ───────────── 전송매체 ─────────────
```

그림의 요지는 LAN 기술이 하나뿐인 것이 아니며, 서로 다른 매체 접근 방식이 IEEE 802 체계 안에 배치된다는 것이다. `802.3 → Ethernet/CSMA/CD`, `802.4 → Token Bus`, `802.5 → Token Ring`, `802.11 → Wireless LAN`의 대응을 자료 기준으로 기억한다. `802.1 Mac Bridging | IEEE 802.1d`는 그림의 표기를 유지한 것으로, 상세 표준 체계나 최신 개정 상태를 이 자료에서 설명하지는 않는다.

### 이해용 예시

두 사람이 같은 전화선을 사용해도 한쪽은 “이 숫자가 목적지”라고 해석하고 다른 쪽은 “이 숫자가 데이터 길이”라고 해석하면 올바른 전달이 어렵다. 선과 신호를 맞추는 문제, 데이터의 의미와 절차를 맞추는 문제가 모두 필요하다.

### 헷갈리기 쉬운 포인트

- IEEE는 조직이며 IEEE 802는 여기서 다루는 표준 체계이다.
- 프로토콜을 프레임 형식 하나로만 축소하지 않는다. 원자료는 물리적·논리적 측면을 함께 열거한다.
- 그림의 모든 표준이 똑같은 매체 접근 방식을 쓴다는 뜻은 아니다.

## 4. 데이터링크 계층을 MAC과 LLC로 나누는 이유

**해당 자료: 6페이지, 데이터 링크 계층의 이층 구조 (IEEE 802)**

### 핵심 개념

자료는 LAN 환경에서 네트워크 자원을 효율적으로 활용하기 위해 데이터링크 계층을 두 하위 계층으로 구분한다. 이유로 Wi-Fi, 이더넷, 블루투스 등 연결 방식의 다양성을 든다.

```text
[6페이지 그림의 텍스트 재구성]

(a) LAN                           (b) WAN
┌──────────────────┐              ┌──────────────────┐
│ 네트워크 계층     │              │ 네트워크 계층     │
├──────────────────┤              ├──────────────────┤
│ LLC 계층         │ ┐            │                  │
├ - - - - - - - - ┤ ├ 데이터링크 │ 데이터링크 계층   │
│ MAC 계층         │ ┘   계층     │                  │
├──────────────────┤              ├──────────────────┤
│ 물리 계층        │              │ 물리 계층        │
└──────────────────┘              └──────────────────┘
```

- **MAC 계층** 은 선로의 종류와 유선·무선 특성에 따라 접근 방식이 달라지는 부분이다.
- **LLC 계층** 은 자료의 설명상 유선·무선 여부와 관계없이 동일한 방식으로 데이터를 처리하는 부분이다.

나누는 이유를 한 문장으로 쓰면, **매체마다 달라지는 접근 규칙과 공통적인 논리적 데이터 처리를 분리하기 위해서** 이다. 매체의 차이가 상위 처리 전체에 그대로 번지지 않도록 역할을 구분한다고 이해하면 된다.

### 이해용 예시

같은 내용을 유선 연결과 무선 연결로 보낸다고 가정하자. “언제 매체를 사용할 수 있는가?”는 연결 방식에 영향을 받지만, “데이터가 잘못되거나 송수신 속도가 다르면 어떻게 처리할까?”는 공통적으로 생각할 수 있다. 이 예시는 자료의 역할 분리를 이해하기 위한 것이다.

### 헷갈리기 쉬운 포인트

- 데이터링크 계층을 두 부분으로 나눈 것이지 OSI 전체에 새 계층 두 개를 추가한 것이 아니다.
- MAC이 물리적 특성을 반영한다고 해서 물리 계층 자체가 되는 것은 아니다.
- 그림에서 WAN 쪽을 하나의 상자로 표현한 사실을 모든 WAN 기술의 내부 구조에 관한 절대 명제로 확대하지 않는다.

## 5. MAC / LLC의 역할·주소·의존성 비교

**해당 자료: 7~9페이지, MAC and LLC Sublayers**

### 핵심 개념 1: MAC은 매체 접근을 담당한다

7페이지의 명칭은 **MAC (Media Access Control Layer)** 이다. 강조 상자에는 “전송 선로 물리 특성 반영, LAN 종류별 상이”라고 적혀 있다.

원자료가 제시하는 주요 방식은 다음과 같다.

- **CSMA/CD**: 공유 버스 방식, 이더넷(Ethernet) 표준.
- **Token Ring**: 점대점 순환 구조에서 토큰 제어 프레임을 순환시키는 방식.

공통 질문은 “여러 호스트 중 누가 지금 전송 매체를 사용할 수 있는가?”이다. CSMA/CD는 충돌을 감지하고 복구하는 방향이고, Token Ring은 토큰으로 권한을 제한하는 방향이다.

### 핵심 개념 2: LLC는 논리적 링크 처리를 담당한다

8페이지의 명칭은 **LLC (Logical Link Control Layer)** 이다. 강조 상자는 송수신 호스트 사이의 프레임 전송에서 물리적인 오류가 발생하면 이를 복구하는 작업을 설명한다.

- **오류 제어(Error Control)**: 데이터의 변형·분실에서 복구한다.
- **흐름 제어(Flow Control)**: 송신 호스트와 수신 호스트 사이의 속도 차이를 조절한다.

오류 제어는 “내용이 손상되거나 사라졌는가?”에, 흐름 제어는 “상대가 처리할 수 있는 속도에 맞추는가?”에 초점을 둔다.

### 9페이지 비교표를 텍스트로 읽기

```text
[9페이지 표의 항목별 재구성]

위치
  MAC: 데이터링크 계층의 하부
  LLC: 데이터링크 계층의 상부

관심사
  MAC: 물리적 매체 접촉, How to access?
  LLC: 데이터 논리 전달, Is it correct?

주요 주소
  MAC: MAC 주소, 하드웨어 주소
  LLC: SAP, 서비스 액세스 포인트

의존성
  MAC: 하드웨어/케이블 종류에 강하게 의존
  LLC: 상위 네트워크 계층과 연계
```

**보충 설명**: SAP(Service Access Point)는 계층 사이에서 서비스를 식별하는 접점이라는 의미이다. 장비를 식별하는 MAC 주소와 같은 종류의 하드웨어 주소로 해석하지 않는다. 이 PDF에는 SAP의 비트 형식이나 구체적인 값은 제시되지 않는다.

### 이해용 예시

공용 발언 장치를 생각해 보자. MAC 관점은 “지금 누가 발언할 차례인가?”이다. LLC 관점은 자료의 설명에 따라 “전달 내용이 손상되지는 않았는가?”, “듣는 쪽의 처리 속도를 넘지 않는가?”이다. 이는 역할을 구분하기 위한 비유이다.

### 헷갈리기 쉬운 포인트

- 오류 제어와 흐름 제어는 같은 기능이 아니다.
- LLC의 설명을 모든 실제 LAN이 항상 같은 재전송 절차를 수행한다는 의미로 확대하지 않는다. **보충 설명**: 구체적인 오류 복구·흐름 제어 기능의 제공 여부는 사용하는 서비스와 구현에 따라 다르다. PDF는 그 세부 구분을 다루지 않는다.
- MAC 주소를 “하드웨어 주소”라고 부른다는 사실만으로 주소가 어떤 상황에서도 바뀔 수 없다는 결론을 내리지 않는다. 이 장의 관심사는 주소의 불변성이 아니라 역할 구분이다.

## 6. 공유 매체의 충돌과 두 가지 해결 전략

**해당 자료: 10페이지, Shared Media Access & Collision**

### 핵심 개념

자료의 기본 전제는 다중 접근 채널에서 데이터 충돌 가능성이 상존한다는 것이다. 여러 호스트가 같은 매체를 사용하면서 동시에 전송하면, 각자의 데이터가 정상적으로 전달되기 어려운 상황이 생긴다. 이것이 이 절에서 다루는 **Collision(충돌)** 이다.

“충돌 가능성이 있다”는 말은 모든 전송이 반드시 충돌한다는 뜻이 아니다. 언제 전송할지를 조정해야 하는 이유를 설명하는 전제이다.

### 전략 A: Collision Detection / Recovery

자료의 표현은 **충돌 허용 및 사후 해결** 이다.

```text
전송 시도 → 충돌 발생 가능 → 충돌 감지 → 재전송으로 복구
```

자료는 CSMA/CD와 Ethernet을 예로 든다. 먼저 경쟁하여 매체를 사용하고, 충돌이 발생하면 감지하여 처리한다. 상세 동작은 18페이지에서 다시 나온다.

### 전략 B: Collision Avoidance / Prevention

자료의 표현은 **충돌 원천 차단** 이다. 전송 권한을 통제하여 동시에 보내는 상황을 막는다. Token Ring이 예시로 제시된다.

```text
전송 시간 또는 권한을 배정 → 허가된 호스트만 전송
```

10페이지는 전송 제어 방법을 다음과 같이 연결한다.

- Ethernet: CSMA/CD를 사용하는 충돌 허용 모델.
- Avoidance: Time Slot을 배정하는 등 전송 시간대를 분리.
- Token Control: Token Bus와 Token Ring. 자료는 이를 “논리적 타임 슬롯 변형 형태”로 설명한다.

토큰을 소유한 동안 전송 기회를 가진다는 점에서 시간 사용 기회를 나누는 것으로 이해할 수 있다. 자료에는 고정 슬롯 길이나 정확한 시간 계산식은 없다.

### 이해용 예시

회의에서 조용해 보이면 누구나 말하는 방식은 두 사람이 동시에 말할 수 있다. 겹치면 멈추고 다시 시도한다. 반면 발언권 카드를 가진 사람만 말하도록 하면 동시 발언을 사전에 제한할 수 있다.

### 헷갈리기 쉬운 포인트

- **감지·복구** 와 **회피·예방** 은 충돌을 다루는 시점이 다르다.
- 10페이지의 Avoidance/Prevention은 넓은 전략 분류이다. 이를 곧바로 특정 CSMA/CA 절차와 동일시하지 않는다.
- **보충 설명**: CSMA/CA라는 이름에 Avoidance가 들어 있어도 모든 충돌이 절대 불가능해지는 것은 아니다. 정상적인 토큰 기반 권한 제어와 CSMA/CA의 경쟁 완화 절차를 구별한다.

## 7. Shared Bus 전송 그림: 모두에게 도달하는 신호와 목적지 수신

**해당 자료: 11페이지, Data Transmission on a Shared Bus**

### 핵심 개념과 그림 해설

그림에는 호스트 1~5가 같은 버스에 연결되어 있다. **5번이 송신 호스트**, **1번이 수신 호스트** 이다. 프레임 안의 `1` 표시는 그림 맥락에서 목적지가 1번임을 나타낸다.

```text
[11페이지 그림의 세 장면을 텍스트로 재구성]

① 송신
  (1)----(2)----(3)----(4)----(5)
                               └─ [목적지 1 | 데이터] 전송
                         ← 버스를 따라 전달

② 호스트별 판단
  (1)          (2)          (3)          (4)
   O            X            X            X
  목적지 일치   목적지 아님   목적지 아님   목적지 아님

③ 전체 전달 관계
  수신 호스트 1  ←────────────────────  송신 호스트 5
```

공유 버스에서는 매체에 실린 신호가 여러 호스트에 도달할 수 있다. 그러나 프레임을 자신에게 온 데이터로 받아들이는 것은 목적지 판단과 관련된다. 그림의 O/X는 이를 구별하기 위한 표시로 읽는다.

### 이해용 예시

교실 전체에 “1번 학생에게 전달할 내용”을 말하면 다른 학생도 소리를 들을 수 있다. 하지만 내용의 수신 대상으로 지정된 사람은 1번 학생이다. 신호에 노출되는 범위와 목적지 지정은 별개의 문제이다.

### 헷갈리기 쉬운 포인트

- 2·3·4번의 X는 선로가 끊겼거나 충돌했다는 표시로 읽지 않는다. 그림은 목적지가 아닌 호스트와 수신 호스트를 대비한다.
- 이 그림 자체는 두 송신자가 동시에 전송하는 충돌 장면이 아니다.
- 여러 호스트에게 신호가 도달한다고 해서 해당 프레임의 목적지 주소가 브로드캐스트 주소인 것은 아니다.

## 8. Token Bus: 물리적 버스와 논리적 링

**해당 자료: 12~13페이지**

### 핵심 개념과 12페이지 그림 해설

자료의 핵심 문구는 **물리적 공유 버스(점선) + 논리적 링 구조(실선)** 이다. 실제 케이블 연결과 토큰이 전달되는 순서를 구분해야 한다.

```text
[12페이지 그림의 연결 관계 재구성]

물리적 연결: 점선으로 그려진 하나의 공유 버스
       6           7           9
       :           :           :
........................................
             :           :
             5           1

논리적 토큰 순서: 실선 화살표
  9 → 7 → 6 → 5 → 1 → 9 → ...
```

호스트 번호와 화살표를 따라가면 토큰은 정해진 순서로 순환한다. 케이블을 새로 원형으로 연결해서 링을 만드는 것이 아니라, 버스에 연결된 호스트들 사이에 논리적인 다음 차례를 정하는 것이다.

동작의 중심은 **토큰(Token), 즉 제어 프레임** 이다. 자료는 이를 이용해 순차적으로 데이터를 전송하며, CSMA/CD의 감지 기반 방식과 다른 전송 방식이라고 설명한다.

### 이해용 예시

위 그림에서 6번이 전송 권한을 사용한 뒤 5번으로 토큰을 넘긴다고 생각해 보자. 1번은 보낼 데이터가 있어도 자기 차례의 토큰을 기다리는 방식으로 이해할 수 있다. 이 설명은 정상적으로 하나의 토큰이 관리되는 상황을 전제로 한 학습용 예시이다.

### 13페이지 Ethernet vs. Token Bus 비교표 해설

```text
[13페이지 표의 텍스트 재구성]

일반 이더넷 (CSMA/CD)
  물리 구조: 공유 버스 / 스타형
  대화 규칙: 자유 경쟁, 충돌 허용
  장점: 단순함, 저렴함
  단점: 부하 증가 시 성능 저하

토큰 버스 (IEEE 802.4)
  물리 구조: 공유 버스
  대화 규칙: 순번제, 토큰 소유
  장점: 충돌 없음, 시간 예측 가능
  단점: 토큰 관리 복잡, 분실 시 복구 등 필요
```

자료의 비교 논리는 명확하다. 경쟁 방식은 전송 기회를 관리하는 규칙이 단순하지만, 많은 호스트가 전송하려 하면 충돌과 재시도 부담이 커진다. 토큰 방식은 순서를 관리하는 부담이 있지만, 전송 기회가 돌아오는 질서를 만들 수 있다.

### 헷갈리기 쉬운 포인트

- Token Bus는 물리적으로 버스이며 논리적으로 링이다. “토큰이 순환하니 케이블도 고리”라고 생각하지 않는다.
- “시간 예측 가능”을 모든 호스트가 항상 즉시 전송한다는 뜻으로 읽지 않는다. 자기 차례까지 기다려야 한다.
- **보충 설명**: 13페이지의 Ethernet 비교는 CSMA/CD를 사용하는 공유 매체·반이중 맥락이다. 전이중 스위치 Ethernet에는 이 충돌 모델을 그대로 적용하지 않는다. 원자료 표의 제목과 내용을 바꾸는 대신 적용 범위를 구분한 것이다.

## 9. Token Ring의 Listen / Transmit Mode

**해당 자료: 14페이지, Token Ring Operational Modes**

### 핵심 개념과 그림 해설

자료는 Token Ring을 순환 전송 매체와 **점대점(Point-to-Point)** 연결 구조로 설명한다. 그림에는 고리, 토큰, 호스트의 인터페이스, 입력단과 출력단이 표시되어 있다.

```text
[14페이지 인터페이스 그림의 기능적 재구성]

이전 이웃 → [입력단 | 인터페이스 | 출력단] → 다음 이웃
                          |
                        호스트

각 인터페이스가 이어져 닫힌 고리를 이룸
토큰도 이 고리를 따라 이동
```

### Listen Mode

원자료는 **입력 비트를 출력단으로 즉시 재전송** 한다고 설명한다. 여기서 Listen은 단순히 아무것도 하지 않고 기다린다는 뜻이 아니다. 다른 곳에서 온 비트가 다음 구간으로 계속 이동하도록 전달한다.

자료에는 “호스트 장애 시 자동 전환으로 네트워크 연속성 유지”도 제시되어 있다. 다만 어떤 회로나 장치가 어떤 장애에서 전환하는지의 상세 조건은 설명하지 않는다.

### Transmit Mode

**토큰을 획득한 뒤 데이터 프레임을 전송할 권한을 보유** 하는 상태이다. 보낼 데이터가 있다는 사실만으로 곧바로 송신 권한을 얻는 것이 아니라 토큰 획득이 조건이다.

```text
[14페이지 내용에 근거한 모드 구별]
Listen:   들어온 비트 → 다음 구간으로 전달
Transmit: 토큰 획득 → 데이터 프레임 전송 권한 행사
```

### 이해용 예시

A → B → C → D → A의 링을 가정하자. B가 Listen Mode이면 A 쪽에서 들어온 비트를 C 쪽으로 전달한다. B가 토큰을 획득하여 데이터를 보낼 때는 Transmit Mode의 역할을 수행한다.

### 헷갈리기 쉬운 포인트

- Listen Mode의 “재전송”은 입력 비트를 다음 구간으로 전달한다는 문맥이다. 오류 발생 후 같은 프레임을 다시 보내는 복구 절차와 구분한다.
- 14페이지의 장애 시 연속성 유지 설명과 15페이지의 “한 곳이 끊기면 전체 마비 가능”을 함께 읽어야 한다. 원자료는 두 문장을 모두 제공한다.
- **보충 설명**: 호스트 장애를 우회하는 경우와 전송 경로 자체가 단절되는 경우는 구별할 수 있다. 다만 구체적인 우회 장치나 보호 방식은 이 PDF만으로 확정할 수 없다. “어떤 장애에도 링이 유지된다”는 결론은 피한다.

## 10. Token Ring vs. Token Bus

**해당 자료: 15페이지**

### 핵심 개념: 권한 제어는 비슷하지만 연결과 다음 순서가 다르다

두 방식 모두 토큰을 이용해 전송 권한을 순차적으로 부여한다. 그러나 Token Ring에서는 물리적 이웃 관계가 중심이며, Token Bus에서는 공유 버스 위에서 논리적인 순서를 정한다.

```text
[15페이지 비교표의 텍스트 재구성]

Token Ring
  물리적 형태: 고리 구조, 케이블이 원형으로 연결
  토큰 전달: 물리적 이웃에게 순서대로 전달
  장점: 구조가 단순하고 공정함, 순차적
  단점: 한 곳만 끊겨도 전체 네트워크 마비 가능

Token Bus
  물리적 형태: 일자형 버스, 호스트가 공통 선로에 연결
  토큰 전달: 주소 순서에 따라 논리적 순번을 정해 전달
  장점: 버스 구조의 설치 편의성 + 링의 질서
  단점: 토큰 관리와 순서 제어 소프트웨어가 복잡함
```

### 이해용 예시

Ring의 “다음 사람”은 고리를 따라 연결된 이웃이다. Bus의 “다음 사람”은 같은 선로에 있는 호스트 중 논리적인 순번으로 지정된 대상이다. 물리적으로 가장 가까운 호스트가 토큰을 다음에 받는다는 보장은 없다.

### 헷갈리기 쉬운 포인트

- 두 방식의 공통점은 토큰이며, 둘 다 물리적으로 링인 것은 아니다.
- 12페이지 화살표는 `9 → 7 → 6 → 5 → 1 → 9`이다. 15페이지의 “주소 순서”를 반드시 오름차순이라고 외우지 않는다.
- 자료는 가입·탈퇴 시 순서 갱신, 토큰 분실 검출 시간, 복구 알고리즘을 제시하지 않는다. “관리 복잡”의 의미를 이해하되 세부 절차를 자료의 내용처럼 만들어 넣지 않는다.

## 11. Collision Domain과 Broadcast Domain, Hub / Switch / Router

**해당 자료: 16~17페이지, Data Collision Issues**

### 핵심 개념: 충돌의 범위와 방송 전달의 범위는 다르다

**Collision Domain** 은 자료의 정의대로 “네트워크상에서 데이터 충돌이 발생할 수 있는 영역”이다.

16페이지에는 `Broardcast Domain`이라는 표기도 보인다. 여기서는 일반적인 영문 철자인 **Broadcast Domain** 으로 병기한다. 자료의 장비 설명을 풀어 쓰면, 브로드캐스트가 함께 전달되는 범위이다. 스위치는 이 범위를 기본적으로 나누지 않고, 라우터는 L3 경계에서 나눈다고 설명한다.

### 16페이지 스위치 그림 해설

```text
[16페이지 그림의 텍스트 재구성]

 H1 ── (Collision Domain #1) ──┐
 H2 ── (Collision Domain #2) ──┤
                              [SW1]
 H3 ── (Collision Domain #3) ──┤
 H4 ── (Collision Domain #4) ──┘

충돌 도메인: 네 구간으로 분리
브로드캐스트 도메인: 자료의 기본 구성에서는 전체가 하나
```

스위치가 호스트 사이의 모든 통신을 하나의 공유 선로처럼 반복하지 않으므로 충돌 영역이 분리된다. 그러나 브로드캐스트는 다른 포트로 전달하므로 충돌 도메인의 개수와 브로드캐스트 도메인의 개수가 같아지지는 않는다.

### Hub: L1, 신호를 복제하는 장비

17페이지에서 허브는 **Collision 1개 / Broadcast 1개** 이다. 핵심 동작은 들어온 신호를 모든 포트로 그대로 복제하여 보내는 것이다.

**이해용 예시**: A, B, C가 하나의 허브에 연결되어 있으면 A가 보낸 신호는 B와 C 쪽에도 전달된다. 자료의 공유 매체 관점에서 세 호스트는 같은 충돌 영역을 공유한다.

**헷갈리기 쉬운 포인트**: 허브는 MAC 목적지를 판단하여 특정 포트만 선택하는 장비가 아니다. 물리적으로 Star여도 동작상 공유 충돌 영역일 수 있다.

### Switch: L2, MAC 주소를 보고 전달하는 장비

17페이지에서 스위치는 **Collision 포트 수만큼 / Broadcast 1개** 이다. 핵심 동작은 MAC 주소를 보고 필요한 포트에 유니캐스트(Unicast)를 전달하는 것이다. 16페이지는 유니캐스트는 나누지만 브로드캐스트는 모든 포트로 전달한다고 설명한다.

**이해용 예시**: A가 보낸 프레임의 목적지가 B이고 B의 포트를 알고 있다면, 스위치는 B 쪽 포트를 선택한다. 같은 구성에서 브로드캐스트 프레임은 다른 포트들에도 퍼질 수 있다.

**헷갈리기 쉬운 포인트**: **보충 설명**: 특정 포트로 보내는 설명은 목적지 위치를 알고 있는 유니캐스트의 기본 경우이다. 목적지를 모르는 유니캐스트는 일반적으로 수신 포트를 제외한 같은 VLAN의 다른 포트로 플러딩한다. VLAN은 브로드캐스트 범위를 나눌 수 있지만 이 장에서는 다루지 않으므로, 원자료의 “1개”는 VLAN 분리를 하지 않은 기본 구성으로 읽는다.

### Router: L3, 네트워크 사이에서 IP를 보고 전달하는 장비

17페이지에서 라우터는 **Collision 포트 수만큼 / Broadcast 포트 수만큼** 이다. 핵심 동작은 IP 주소를 보고 서로 다른 네트워크로 길을 찾아주는 것이다. 16페이지는 포트마다 서로 다른 브로드캐스트 도메인을 형성한다고 설명한다.

```text
[16~17페이지 내용에 근거한 이해용 도식]

[LAN A: Broadcast Domain A] ── [Router] ── [LAN B: Broadcast Domain B]
             L2 방송 범위의 경계 ↑
```

**이해용 예시**: 두 LAN을 라우터의 서로 다른 포트에 연결한다. 자료의 기본 모델에서는 한 LAN의 브로드캐스트 범위가 다른 LAN과 분리된다.

**헷갈리기 쉬운 포인트**: 라우터가 브로드캐스트 도메인을 나눈다는 것은 서로 다른 네트워크 간 통신을 모두 막는다는 뜻이 아니다. IP에 근거해 네트워크 사이의 데이터를 전달한다.

### 도메인 개수 문제의 적용 조건

```text
[17페이지 표의 개수 관계를 그대로 재구성]

장비            Collision             Broadcast
Hub (L1)        1개                   1개
Switch (L2)     포트 수만큼            1개
Router (L3)     포트 수만큼            포트 수만큼
```

**보충 설명**: 위 표는 기본 연결 모델이다. 실제 도메인 수를 셀 때는 연결된 포트, 공유 구간, VLAN, 라우팅 인터페이스 등을 확인해야 한다. 특히 전이중 링크에서는 CSMA/CD 충돌이 발생하지 않는다. 교재식 “포트별 충돌 도메인 분리”와 “실제로 충돌이 발생한다”를 동일시하지 않는다.

## 12. CSMA/CD: Carrier Sense → Multiple Access → Collision Detection

**해당 자료: 18페이지, 앞선 7·10·16~17페이지와 연결**

### 핵심 개념

원자료의 제목은 `CSMA/CD (Carrier Sence Multiple Access with Collision Detection)`이다. `Sence`는 원자료 표기이며, 아래에서는 통상 철자인 **Carrier Sense** 를 함께 사용한다.

1. **Carrier Sense**: 케이블에 흐르는 신호, 즉 반송파를 감지한다. 전송 전에 매체가 사용 중인지 살핀다는 의미이다.
2. **Multiple Access**: 여러 컴퓨터가 하나의 네트워크에 접속하도록 허용한다. 매체를 사용할 수 있는 참여자가 여럿이다.
3. **Collision Detection**: 전송 도중 충돌을 감지한다. 충돌이 발생하면 전송을 중단하고 임의의 시간을 기다렸다가 다시 시도한다.

Multiple Access는 Carrier Sense 다음에 실행하는 별도 검사 단계라기보다, 여러 호스트가 매체를 공유한다는 환경의 성질이다. 실제 동작 순서는 감지 → 전송 → 전송 중 충돌 감시 → 필요 시 대기·재시도이다.

```text
[18페이지 설명을 흐름으로 재구성]

보낼 데이터가 있음
        ↓
매체의 신호 감지 (Carrier Sense)
        ↓
사용 중인가? ── 예 → 기다린 뒤 다시 감지
        │
       아니오
        ↓
전송 시작
        ↓
전송하면서 충돌 감시 (Collision Detection)
        ↓
충돌했는가? ── 아니오 → 전송 계속 → 완료
        │
        예
        ↓
전송 중단 → 임의 시간 대기 → 다시 전송 시도

배경 조건: 여러 호스트가 같은 매체 사용 (Multiple Access)
```

### 이해용 예시: 먼저 들어 보는데도 왜 충돌할까?

자료는 두 컴퓨터가 모두 비어 있다고 판단하고 데이터를 전송하는 상황을 설명한다. A와 B가 비슷한 시점에 매체를 확인하면 둘 다 전송을 시작할 수 있다.

**보충 설명**: 한쪽에서 전송한 신호가 다른 쪽에 도달하기까지는 시간이 걸린다. 따라서 “내 위치에서 지금 신호가 들리지 않는다”는 판단이 다른 곳의 동시 전송 가능성까지 제거하지는 않는다.

### 헷갈리기 쉬운 포인트

- Carrier Sense만으로 충돌을 완전히 예방하지는 못한다.
- Collision Detection은 전송을 모두 끝낸 뒤에만 수행하는 확인이 아니다. 자료는 **전송 도중 감지** 를 강조한다.
- 18페이지의 임의 대기는 **충돌 발생 후** 의 재시도 설명이다. 다음 19페이지의 “비어 있어도 먼저 대기”와 같은 문장으로 합쳐 외우지 않는다.
- 자료는 Jam Signal, 이진 지수 백오프의 계산식, 최소 프레임 길이 등을 설명하지 않는다. 여기서는 PDF의 절차 범위에 집중한다.

## 13. 19페이지 주의: CSMA/CD 제목과 CSMA-CA 그림의 차이

**해당 자료: 19페이지**

### 핵심 개념: 원자료의 표기를 보존하면서 불일치를 구별한다

**이 페이지의 제목은 CSMA/CD이지만, 그림에는 CSMA-CA와 RTS/CTS/data/ack가 표시되어 있다.** 본문도 매체가 비어 있더라도 전송 전에 임의 시간 대기, 전송 후 ACK 확인을 설명한다. 따라서 18페이지의 CSMA/CD 설명과 그대로 합치면 개념이 섞일 수 있다.

이 학습노트는 제목을 CSMA/CA로 임의 교체하지 않는다. “19페이지는 CSMA/CD라는 제목 아래 CSMA/CA 흐름으로 보이는 그림과 설명이 함께 배치되어 있다”는 자료상의 차이를 기록한다.

### 원자료가 실제로 제시하는 내용

- 제목: `CSMA/CD (Carrier Sence Multiple Access with Collision Detection)`.
- Carrier Sense: 전송 전에 네트워크가 사용 중인지 확인.
- Random Backoff: 네트워크가 비어 있어도 바로 전송하지 않고 임의 시간 대기.
- ACK Confirmation: 데이터를 전송한 뒤 목적지에서 잘 받았는지 확인.
- 그림: source, destination, others의 시간축과 RTS, CTS, data, ack.
- 그림의 추가 표시: DIFS, SIFS, `NAV: defer access`, 하단 `CSMA-CA`.

```text
[19페이지 그림의 텍스트 재구성: 시간은 아래로 진행]

source                    destination                 others
  |                            |                        |
 DIFS                          |                        |
  | -------- RTS ------------> |                        | 전송 보류
  |                           SIFS                      | NAV:
  | <------- CTS ------------- |                        | defer access
 SIFS                          |                        |
  | -------- data -----------> |                        |
  |                           SIFS                      |
  | <------- ack ------------- |                        |
  |                            |                        |

그림 하단 표기: CSMA-CA
```

### 보충 설명: 그림의 용어를 읽는 데 필요한 최소 배경

- RTS(Request to Send)는 전송 요청, CTS(Clear to Send)는 전송 허가 응답으로 읽는다.
- DATA는 실제 데이터, ACK(Acknowledgment)는 수신 확인이다.
- 그림의 DIFS/SIFS는 프레임 교환 사이의 대기 간격을 나타낸다. 원자료에는 수치나 상세 규칙이 없다.
- NAV(Network Allocation Vector)는 다른 장치가 매체 사용을 미루는 예약 시간 정보와 관련된다. 그림의 `others`는 접근을 보류한다.
- 이 그림은 RTS/CTS를 사용하는 CSMA/CA 교환의 전형적인 형태이다. 모든 CSMA/CA 전송에 RTS/CTS가 반드시 붙는다는 의미로 확대하지 않는다.
- Random Backoff라는 말만으로 CD와 CA를 구별할 수는 없다. 18페이지에도 충돌 후 임의 대기가 있다. 구별의 핵심은 대기의 맥락과 RTS/CTS/ACK 등 전체 절차이다.

### 이해용 예시

18페이지는 “둘이 동시에 말하다 겹치면 멈추고 기다렸다 다시 말하기”로 생각할 수 있다. 19페이지 그림은 “전송을 요청하고 응답을 받은 뒤 데이터를 보내며 수신 확인을 받는 교환”으로 읽는다. 두 그림을 각자의 페이지 맥락으로 설명하는 연습을 한다.

### 헷갈리기 쉬운 포인트와 미확정 부분

- RTS/CTS/ACK를 18페이지 CSMA/CD의 필수 절차로 적지 않는다.
- 19페이지 제목과 그림 사이에 차이가 있다는 사실은 확인할 수 있다.
- 이것이 편집 오류인지, 비교 설명을 위한 배치인지, 교수의 구두 설명이 있었는지는 PDF만으로 확정할 수 없다.
- 시험에서 19페이지를 직접 묻는다면 원자료의 표기와 개념 구분을 함께 기술하는 것이 학습상 안전하다. 공식 채점 기준은 자료에 없다.

## 14. Review Q1: 스위치의 MAC 주소 업데이트

**해당 자료: 20페이지**

### 원문 질문과 보기

> Q1. 새 컴퓨터가 스위치 연결되면 스위치는 새 컴퓨터의 MAC 주소를 모른다. 그럼 스위치에서 MAC 주소를 어떻게 업데이트 할까?

```text
① CDMA/CA
② Token Ring
③ ARP
④ CMDA/CD
⑤ RARP
```

①의 `CDMA/CA`와 ④의 `CMDA/CD`는 PDF의 철자를 그대로 옮겼다. 이를 조용히 CSMA/CA 또는 CSMA/CD로 바꾸어 제시하지 않는다.

### 핵심 개념: 자료가 제공하는 범위

17페이지는 스위치가 MAC 주소를 보고 포트를 선택한다고 설명한다. 20페이지는 위 질문과 보기만 제공하며 **정답 표시와 해설은 없다**. MAC 테이블 학습 절차, ARP/RARP의 정의도 이 PDF 본문에는 제시되지 않는다.

따라서 PDF만으로 “교수가 지정한 정답은 ③이다”라고 확정할 수 없다. 무엇을 업데이트한다는 질문인지도 구별해야 한다. 스위치의 MAC 주소-포트 대응 정보와 호스트의 IP-MAC 대응 정보는 같은 표가 아니다.

### 보충 설명: 일반적인 L2 스위치의 학습 원리

스위치는 수신한 프레임의 **출발지 MAC 주소** 와 **수신 포트** 를 연결하여 MAC 주소 테이블을 학습한다. 이 학습은 ARP 프레임에만 한정되지 않는다.

```text
[보충 설명을 위한 예시: PDF에 없는 상세 동작]

새 PC A ── 스위치 포트 3

A가 보낸 프레임:
  출발지 MAC = A의 MAC
  목적지 MAC = 상대의 MAC 또는 브로드캐스트 주소 등

스위치가 포트 3으로 프레임 수신
  → 출발지 MAC 확인
  → "A의 MAC은 포트 3 쪽에 있음" 학습
```

ARP(Address Resolution Protocol)는 일반적인 IPv4 LAN 맥락에서 IP 주소에 대응하는 MAC 주소를 알아내는 데 사용된다. 새 PC가 ARP 프레임을 보내면 스위치가 그 프레임의 출발지 MAC을 학습할 수는 있다. 하지만 이는 **프레임을 받아 출발지를 학습한 것** 이지, 스위치의 일반 학습 원리가 ARP라는 뜻은 아니다.

RARP(Reverse Address Resolution Protocol)는 MAC 주소를 바탕으로 IP 주소를 알아내는 역방향 주소 해석과 관련된 용어이다. 이것도 스위치의 일반 MAC 테이블 학습 원리와 구별된다. Token Ring은 자료에서 다룬 매체 접근 방식이다. ①·④의 철자는 원문 표기만으로 정확한 의도를 확정하지 않는다.

### 이해용 예시와 답안 정리

새 PC가 ARP 요청을 보내는 상황을 떠올리면, “보기에서 ARP를 의도했을 가능성”과 “실제 스위치의 출발지 MAC 학습”이 어떻게 연결되는지는 설명할 수 있다. 그러나 그 가능성을 공식 정답으로 바꾸면 안 된다.

서술형 복습 답안은 다음처럼 정리할 수 있다.

> 일반적인 L2 스위치는 수신 프레임의 출발지 MAC 주소와 수신 포트를 연결해 학습한다. ARP 프레임도 학습의 계기가 될 수 있지만 ARP만으로 학습하는 것은 아니다. 이 슬라이드는 선택지의 정답을 표시하지 않아 교수의 의도된 정답은 자료만으로 확정하기 어렵다.

### 헷갈리기 쉬운 포인트

- “PC의 MAC 주소 자체를 변경한다”는 질문으로 읽지 않는다. 문맥은 스위치가 새 PC의 위치 정보를 알아가는 문제이다.
- 전달할 포트를 고를 때 보는 목적지 MAC과, 학습할 때 보는 출발지 MAC을 구별한다. 후자는 보충 설명이다.
- ARP 캐시와 스위치 MAC 주소 테이블을 같은 것으로 외우지 않는다.

## 15. Review Q2: IPv6는 왜 128 bits인가?

**해당 자료: 21페이지**

### 핵심 개념: 표기 길이의 계산과 설계 이유를 구별한다

원자료 질문은 “ipv6 주소. 왜 128 bits라고 하는가?”이며 다음 예시를 제공한다.

```text
fe80:0000:0000:0000:50cd:fd4a:c05c:666a >> 128bits
```

이 예시로 **주어진 주소가 128비트임을 계산** 할 수 있다. 반면 IPv6 설계자가 다른 길이가 아니라 왜 128비트를 선택했는지에 관한 역사적·설계적 이유는 이 페이지에 없다.

### 자료의 예시를 이용한 계산

**보충 설명: 진법 계산의 기초** — 16진수 한 자리는 16가지 값을 나타내며, `16 = 2^4`이므로 4비트에 해당한다.

```text
[21페이지 주소 예시 분해]

fe80 : 0000 : 0000 : 0000 : 50cd : fd4a : c05c : 666a
 ①      ②      ③      ④      ⑤      ⑥      ⑦      ⑧

그룹 수                = 8
각 그룹의 16진수 자릿수 = 4
16진수 한 자리         = 4 bits

8 × 4 × 4 = 128 bits
```

콜론은 그룹을 구분하는 표기이며 주소 비트 수에 더하지 않는다. 따라서 이 질문을 “표시된 주소의 길이를 설명하라”는 의미로 읽으면 **8그룹 × 그룹당 16비트 = 128비트** 로 답할 수 있다.

### 이해용 예시

첫 그룹 `fe80`만 이진수로 바꾸면 다음과 같다.

```text
f    e    8    0
1111 1110 1000 0000  → 총 16비트
```

같은 길이의 그룹이 8개이므로 총 128비트이다. 이 이진수 변환은 원자료 예시에 대한 계산 풀이이다.

### 자료만으로 확정하기 어려운 부분

- “왜 64비트나 256비트 대신 128비트로 표준화했는가?”에 대한 설계 배경.
- 예시 주소의 접두부 의미나 인터페이스 식별자 생성 방식.
- 주소 축약 표기의 상세 규칙.

### 헷갈리기 쉬운 포인트

- 16진수 네 자리를 4비트라고 세지 않는다. 네 자리는 16비트이다.
- 콜론까지 포함한 문자열 길이를 비트 수로 환산하지 않는다.
- “이 표기가 128비트인 이유”와 “128비트를 선택한 설계 이유”는 별개의 질문이다. 이 PDF는 전자의 계산을 위한 예시를 제공한다.

## 17. 시험 대비 핵심

아래는 PDF의 반복·비교 항목을 바탕으로 만든 복습 우선순위이며, 교수의 출제 예고나 공식 정답표는 아니다.

### 핵심 개념: 설명할 수 있어야 하는 항목

1. **거리 분류**: PAN → LAN → MAN → WAN과 3페이지의 대표 거리 수치를 연결한다.
2. **여섯 토폴로지**: 그림만 보고 Bus/Ring/Mesh/Star/Tree/Hybrid를 구별한다.
3. **프로토콜의 두 측면**: 물리적 측면의 매체·단자·신호, 논리적 측면의 프레임·주소·오류·흐름·절차를 구분한다.
4. **IEEE 802**: 자료 그림의 802.2 LLC, 802.3 Ethernet, 802.4 Token Bus, 802.5 Token Ring, 802.11 Wireless LAN을 연결한다.
5. **MAC/LLC 분리 이유**: 매체별 접근 차이와 공통적인 논리 처리를 분리한다고 설명한다.
6. **MAC/LLC 비교**: 하부/상부, How to access?/Is it correct?, MAC 주소/SAP, 매체 의존/상위 계층 연계를 말한다.
7. **충돌 전략**: Detection/Recovery와 Avoidance/Prevention의 차이를 설명한다.
8. **Shared Bus 그림**: 신호가 여러 호스트에 도달하는 것과 목적지 호스트가 받아들이는 것을 구별한다.
9. **Token Bus**: 물리적 버스 + 논리적 링, 순차적 권한 부여, 토큰 관리 복잡성을 설명한다.
10. **Token Ring**: Listen의 비트 전달, Transmit의 토큰 기반 송신 권한을 구별한다.
11. **도메인**: 허브 1/1, 스위치 포트별/1, 라우터 포트별/포트별을 원자료의 기본 모델로 설명한다.
12. **CSMA/CD**: 감지, 공유 접근, 전송 중 충돌 감시, 중단·임의 대기·재시도를 연결한다.
13. **19페이지 차이**: CSMA/CD 제목과 CSMA-CA 그림을 둘 다 정확히 소개한다.
14. **Review의 범위**: Q1 정답 미표시와 MAC 학습 보충 원리를 구별하고, Q2의 `8 × 4 × 4`를 계산한다.

### 이해용 예시: 짧은 서술형 답안 연습

> MAC은 매체 특성에 맞는 접근을 담당하고, LLC는 자료의 설명상 오류·흐름 제어 등 논리적 처리를 담당한다. 이렇게 나누면 다양한 유선·무선 연결 방식의 차이를 MAC 쪽에서 다루면서 상위의 논리적 처리를 구분할 수 있다.

> Token Bus는 실제 연결은 공유 버스이지만 토큰 전달 순서는 논리적 링이다. Token Ring은 자료에서 물리적 고리의 이웃을 따라 토큰을 전달한다. 둘 다 토큰을 이용하지만 물리 구조와 다음 순서의 결정 방식이 다르다.

### 헷갈리기 쉬운 포인트: 마지막 확인

- “스위치가 충돌 도메인을 나눈다”와 “브로드캐스트도 나눈다”를 같은 말로 쓰지 않는다.
- “Carrier Sense를 하니 충돌하지 않는다”라고 쓰지 않는다.
- “Listen은 아무것도 하지 않는 상태”라고 쓰지 않는다.
- “Token Bus의 케이블은 링”이라고 쓰지 않는다.
- “19페이지의 RTS/CTS/ACK가 CSMA/CD의 필수 과정”이라고 쓰지 않는다.
- “Q1의 ③이 자료에 표시된 정답”이라고 쓰지 않는다.
- “Q2의 비트 수 계산이 IPv6의 역사적 설계 이유까지 증명한다”라고 쓰지 않는다.

13. Ring은 물리적 이웃, Bus는 주소에 따른 논리적 순번.
14. 자료의 기본 구성에서 충돌 도메인 4개, 브로드캐스트 도메인 1개.
15. 허브는 신호 복제, 스위치는 MAC에 따른 포트 선택, 라우터는 IP에 따른 네트워크 간 전달.
16. 자료는 두 컴퓨터가 모두 비어 있다고 판단하는 상황을 설명한다. 전파 지연은 이를 이해하기 위한 보충 설명이다.
17. 전송 중 충돌 감지 → 전송 중단 → 임의 시간 대기 → 재시도.
18. 제목은 CSMA/CD, 본문에는 전송 전 임의 대기·ACK 확인, 그림에는 RTS/CTS/data/ack와 CSMA-CA가 있다. 편집 의도는 미확정이다.
19. PDF에는 질문·보기만 있고 정답은 없다. 보충 원리는 수신 프레임의 출발지 MAC과 수신 포트를 연결해 학습한다는 것이다. ARP만으로 학습하는 것은 아니다.
20. 8그룹 × 4자리 × 4비트 = 128비트. 왜 그 길이로 설계했는지의 역사적 이유는 계산만으로 알 수 없다.

### 이해용 적용 문제

PC A, B, C, D가 하나의 중앙 장비에 연결되어 있다고 가정한다. 중앙 장비가 허브일 때와 스위치일 때, A의 유니캐스트 프레임을 어떻게 다루는지 설명해 보라. 이어서 라우터로 다른 LAN을 연결하면 브로드캐스트 범위가 어떻게 되는지 말해 보라.

**확인 방향**: 허브는 신호를 복제한다. 스위치는 목적지 MAC의 포트를 알고 있을 때 그 포트를 선택한다. 라우터는 자료의 기본 모델에서 두 LAN의 브로드캐스트 도메인을 나눈다. 스위치의 목적지 미학습 처리나 VLAN은 본문의 보충 설명 범위이다.
