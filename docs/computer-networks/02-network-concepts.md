## 2. Introduction to Networking

### 2.1 인터넷과 소프트웨어의 관계

**자료: p.3**

슬라이드는 Internet 아래에 Software, Real-time Verification, Monitoring, Confirmation, Core Software Technologies라는 키워드를 제시한다. 오른쪽에는 여러 장치와 서비스 아이콘이 인터넷을 중심으로 연결된 이미지가 있다.

이 페이지에는 각 키워드의 엄밀한 정의나 특정 도구의 사용법은 없다. 학습 관점에서는 **네트워크가 하드웨어 연결에만 머무르지 않고 소프트웨어의 실행·관찰·확인과 연결된다** 는 도입으로 이해하면 된다.

**보충 예시:** 사용자가 서버에 요청을 보냈다는 사실과, 서버가 요청을 받아 정상 처리했다는 사실은 다르다. 통신 상태를 관찰하는 Monitoring과 실제 결과를 확인하는 Confirmation이 필요한 이유를 이런 상황으로 생각할 수 있다. 이 비유를 별도의 네트워크 표준 기능 정의로 암기하지는 않는다.

그림 속 여러 아이콘은 다양한 서비스가 공통 네트워크 기반을 이용한다는 의미다. 인터넷이 특정 기기나 특정 소프트웨어 하나라는 뜻이 아니다.

### 2.2 인터넷 역사에서 구분할 이름

**자료: p.4**

강의자료에 나오는 인물과 대상을 구분한다.

- **Vint Cerf와 Bob Kahn:** TCP/IP 프로토콜 설계와 연결되는 인물.
- **Tim Berners-Lee:** WWW(World Wide Web)의 창시자.
- **ARPANET:** 초기 컴퓨터 네트워크이자 인터넷 발전의 중요한 선행 네트워크.
- **J. C. R. Licklider:** 컴퓨터 네트워크의 구상과 연결되는 인물.

학습의 연결 고리는 다음과 같다.

```text
컴퓨터들을 연결해 자원과 정보를 이용하려는 구상
    ↓
ARPANET과 같은 초기 네트워크
    ↓
다양한 네트워크를 연결하는 공통 프로토콜의 발전
    ↓
그 기반 위에서 WWW와 같은 서비스 등장
```

이는 개념 연결용 흐름이다. 슬라이드에는 상세 연대표가 없으므로 모든 개발이 한 줄로만 진행되었다고 해석하지 않는다.

**인터넷과 WWW의 구분:** 인터넷은 네트워크들이 연결된 통신 기반이고, WWW는 웹 문서와 자원을 이용하는 서비스 체계다. 따라서 TCP/IP 설계자와 WWW 창시자를 같은 질문의 정답처럼 바꾸어 쓰면 안 된다.

ARPANET의 개발 목적과 최초 메시지는 3장의 Review에서 다시 다룬다. 특히 ‘핵전쟁 대비가 유일한 개발 목적’이라는 설명은 역사적 사실과 구분해야 하므로 [3장 Review 해설](03-network-technologies.md#10-review-문제와-상세-해설)을 함께 참고한다.

## 3. Network Fundamentals: 네트워크 3요소

### 3.1 Coffee 도식: 점·선·규칙

**자료: p.5**

‘Break Time – Coffee’ 슬라이드는 세 요소를 일상적인 통화에 비유한다.

```text
Node      → 연결의 점   → 사람
Link      → 연결의 선   → 전화선
Protocol  → 연결의 규칙 → 언어
```

사람 둘이 있다고 통화가 되는 것은 아니다. 소리가 전달되는 통로가 있어야 하고, 상대의 말을 해석할 공통 규칙도 필요하다. 네트워크도 **주체·통로·규칙** 이 함께 있어야 한다.

비유의 한계도 있다. 실제 프로토콜은 말의 종류뿐 아니라 메시지 형식, 순서, 응답 방식 등도 규정할 수 있다. 또 Link가 반드시 눈에 보이는 전선인 것은 아니다.

### 3.2 Node — 연결되어 데이터를 주고받는 주체

**자료: p.5~6**

**Node(노드)** 는 네트워크에 연결되어 데이터를 보내거나 받거나 중계하는 장치 또는 시스템이다. 자료의 예시는 스마트폰과 서버다.

노드를 이해할 때는 ‘사람이 사용하는 컴퓨터’로만 범위를 좁히지 않는다. 네트워크에 연결된 센서, 키오스크, 스마트 가전도 통신 주체가 될 수 있다. 중간에서 전달을 돕는 장치도 노드에 포함된다.

**보충 예시:** 스마트폰이 서버에 사진을 업로드하면 스마트폰과 서버는 통신의 양 끝에 있는 노드다. 그 사이에서 데이터를 전달하는 장비는 중계 역할의 노드다. 3장에서 End Node와 Intermediate Node를 구분한다.

**반례:** Wi-Fi 비밀번호는 장치나 통신 주체가 아니라 인증에 사용하는 정보이므로 Node가 아니다.

### 3.3 Link — 데이터가 전달되는 통로

**Link(링크)** 는 노드 사이를 연결하는 물리적 또는 논리적 통로다.

- 물리적 관점: 구리 케이블, 광섬유, 무선 신호가 전달되는 경로.
- 논리적 관점: 실제 물리적 구성을 추상화하여 연결 관계로 표현한 통로.

자료에는 광케이블·랜선, Bluetooth·Wi-Fi가 예시로 나온다. 여기서 분류를 정교하게 읽어야 한다. 광케이블·랜선은 물리적 전송 매체의 예이고, Bluetooth·Wi-Fi는 무선 링크를 제공하는 통신 기술이다. 후자의 기술에도 규칙과 표준이 포함되므로 ‘Link이므로 Protocol과 아무 관계가 없다’고 이해하면 안 된다.

**보충 예시:** 방 안의 노트북과 무선 접속 장비 사이에 케이블이 보이지 않아도 무선 연결이라는 Link가 존재한다. 반대로 케이블이 꽂혀 있어도 신호나 규칙이 맞지 않으면 유효한 데이터 교환이 성립하지 않을 수 있다.

### 3.4 Protocol — 메시지를 해석하고 주고받는 규칙

**Protocol(프로토콜)** 은 통신 당사자가 데이터를 교환할 때 따르는 약속이다. 자료에서는 ‘공식적인 약속’, TCP/IP를 연결해 제시한다.

이해를 돕기 위해 규칙을 세 가지 질문으로 나눌 수 있다.

1. **형식:** 어떤 항목을 어떤 구조로 보낼 것인가?
2. **의미:** 받은 각 항목을 어떻게 해석할 것인가?
3. **절차:** 어떤 메시지 다음에 무엇을 보내고, 언제 응답할 것인가?

위 세 질문은 프로토콜을 읽기 위한 보충 설명이다. 슬라이드가 별도의 세부 암기 목록을 제시한 것은 아니다.

**예시:** 한쪽이 어떤 바이트를 ‘요청 길이’로 해석하고 다른 쪽이 ‘명령 종류’로 해석한다면, 신호가 도착해도 정상적인 대화가 되지 않는다. 따라서 연결 성공과 의미 있는 통신 성공은 다르다.

### 3.5 p.6의 나열을 올바르게 연결하기

p.6은 요소, 정의, 예시를 서로 다른 상자에 나열한다. 같은 높이에 놓인 항목끼리 단순히 연결하면 정의가 어긋날 수 있다. p.5의 비유와 개념을 기준으로 다음처럼 대응시킨다.

- Node ↔ 연결된 모든 장치 ↔ 스마트폰·서버.
- Link ↔ 물리적·논리적 통로 ↔ 광케이블·랜선·무선 연결.
- Protocol ↔ 통신의 약속 ↔ TCP/IP.

핵심 문장: **노드가 링크를 통해 프로토콜에 따라 데이터를 주고받는다.**

## 4. Layered Models: 통신을 계층으로 나누는 이유

**자료: p.7~8, 보충 설명 포함**

네트워크 3요소가 ‘무엇이 필요한가’에 대한 답이라면, 계층 모델은 ‘통신 기능을 어떻게 나누어 설명할 것인가’에 대한 답이다.

웹페이지를 받는 일에는 서비스 요청 작성, 응용 통신 대상 구분, 목적지 주소 확인, 각 링크에서의 전달, 신호 송수신이 모두 포함된다. 역할을 계층으로 나누면 각 문제를 독립적으로 이해하면서도 전체 흐름을 연결할 수 있다.

### 4.1 수직 관계: 같은 시스템 안의 서비스 이용

위 계층은 아래 계층이 제공하는 기능을 이용한다. 응용 계층이 데이터를 전달하려 할 때 모든 전기 신호 처리 방법을 직접 구현할 필요는 없다. 아래 계층에 필요한 전달을 맡기는 구조로 이해한다.

### 4.2 수평 관계: 상대 시스템의 같은 계층과 공통 규칙

송신 측과 수신 측의 같은 계층은 서로 해석 가능한 프로토콜을 사용한다. 이를 논리적인 같은 계층 간 통신으로 표현한다.

```text
송신 측                         수신 측
응용 계층  - - 논리적 대응 - -  응용 계층
   ↓                               ↑
전송 계층  - - 논리적 대응 - -  전송 계층
   ↓                               ↑
네트워크   - - 논리적 대응 - -  네트워크
   ↓                               ↑
하위 계층  == 매체와 중간 장비 == 하위 계층
```

점선은 직접 연결된 별도의 전선이 아니다. 실제 데이터는 송신 시스템에서 내려가고, 매체와 중간 장비를 거쳐 수신 시스템에서 올라간다.

## 5. OSI 7계층의 역할

**자료: p.7~8**

**OSI(Open Systems Interconnection)** 는 통신 기능을 7개 계층으로 구분하는 참조 모델이다. 슬라이드에서는 ISO와 연결해 제시한다. 아래 설명은 p.8의 간결한 역할 문장을 자습 가능한 수준으로 풀어 쓴 것이다.

### 5.1 7계층 — Application Layer, 응용 계층

- 자료의 핵심 표현: 사용자가 직접 사용하는 프로그램.
- 기능 관점의 해설: 응용 프로그램이 네트워크 서비스를 이용하기 위한 통신 기능과 메시지 규칙.
- 기본 PDU 표기: Data.

웹 요청이나 이름 조회처럼 서비스 목적에 맞는 데이터를 주고받는 단계다. 사용자의 요청을 네트워크 통신의 의미 있는 메시지로 표현하는 데 초점을 둔다.

**헷갈림 방지:** 브라우저 전체가 곧 OSI 7계층이라는 뜻은 아니다. 브라우저의 화면 표시, 파일 저장 등 여러 기능 중 네트워크 서비스와 관련된 부분을 계층 관점으로 설명하는 것이다.

### 5.2 6계층 — Presentation Layer, 표현 계층

- 자료의 핵심 표현: 데이터를 적절한 형식으로 변환.
- 기능 관점의 해설: 서로 이해할 수 있는 데이터 표현을 맞추는 역할.
- 기본 PDU 표기: Data.

동일한 데이터라도 표현 방식이 맞지 않으면 수신 측이 내용을 제대로 해석할 수 없다. 자료의 오른쪽 그림은 Data Representation and Encryption을 함께 언급한다.

**보충 예시:** 문자 데이터를 어떤 인코딩으로 표현할지, 압축·암호화된 정보를 어떤 방식으로 처리할지와 연결해 생각할 수 있다. 다만 실제 인터넷 구현의 모든 암호화 기능이 독립된 ‘OSI 6계층 모듈’에만 존재한다는 뜻은 아니다.

### 5.3 5계층 — Session Layer, 세션 계층

- 자료의 핵심 표현: 두 장치 간 통신 설정 및 관리.
- 기능 관점의 해설: 응용 사이의 대화 관계를 설정하고 유지·관리하는 역할.
- 기본 PDU 표기: Data.

단순히 메시지 하나를 전달하는 것과, 여러 메시지를 하나의 대화로 관리하는 것은 다른 문제다. 세션 계층은 후자의 관점으로 이해한다.

**헷갈림 방지:** 여기서 말하는 세션을 웹 로그인 세션이나 TCP 연결과 무조건 같은 것으로 보면 안 된다. 같은 단어가 서로 다른 추상화 수준에서 쓰일 수 있다. TCP 연결 설정은 전송 계층의 기능으로 다룬다.

### 5.4 4계층 — Transport Layer, 전송 계층

- 자료의 핵심 표현: 데이터를 Segment로 분할, 신뢰성.
- 기능 관점의 해설: 양 끝 호스트의 응용 프로그램 사이에 데이터를 전달하는 전송 서비스.
- 핵심 식별 정보: Port.
- 기본 PDU 표기: Segment, TCP 기준.

한 컴퓨터에서 웹, 메일 등 여러 프로그램이 통신할 수 있으므로 목적지 컴퓨터에 도착하는 것만으로는 충분하지 않다. 어떤 응용 통신으로 전달할지를 구분해야 한다. 이때 Port 번호가 중요하다.

자료는 신뢰성을 전송 계층의 대표 역할로 제시한다. **TCP** 는 순서 있는 신뢰성 전송을 제공하고, **UDP** 는 TCP와 동일한 신뢰성·순서 보장을 자체 제공하지 않는다. 따라서 ‘전송 계층의 모든 프로토콜이 신뢰성을 보장한다’는 문장은 틀리다.

또한 ‘분할’은 큰 데이터를 전송 단위로 나눌 수 있다는 설명이다. 모든 전송마다 반드시 여러 조각으로 나뉜다는 뜻은 아니다.

### 5.5 3계층 — Network Layer, 네트워크 계층

- 자료의 핵심 표현: Segment를 Packet으로 변환, IP 전송.
- 기능 관점의 해설: 논리적 주소를 이용해 여러 네트워크를 거쳐 목적지로 전달.
- 핵심 식별 정보: IP 주소.
- 기본 PDU 표기: Packet.

출발지와 목적지가 직접 연결되어 있지 않아도 중간 장비들을 통해 전달할 수 있어야 한다. 이때 목적지 주소와 경로에 관한 기능이 필요하다.

**‘변환’의 정확한 의미:** 전송 계층의 정보가 없어지고 전혀 다른 내용이 되는 것이 아니다. 일반적인 캡슐화 설명에서는 Segment를 내부 데이터로 담고 IP 헤더를 붙여 Packet을 구성한다.

### 5.6 2계층 — Data Link Layer, 데이터 링크 계층

- 자료의 핵심 표현: Packet을 Frame으로 변환, MAC 전송.
- 기능 관점의 해설: 현재 링크에서 사용할 프레임 구조와 링크 수준의 전달 처리.
- 핵심 식별 정보: Ethernet 예시에서 MAC 주소.
- 기본 PDU 표기: Frame.

멀리 있는 최종 목적지로 보내려 해도, 실제로는 먼저 현재 연결에서 다음 장치로 전달해야 한다. 이 계층은 그 구간에서 사용할 형식과 주소를 다룬다.

**보충 예시:** 목적지가 다른 네트워크에 있다면 현재 링크의 프레임은 다음 전달 장치로 향할 수 있다. 따라서 현재 프레임의 목적지 MAC 주소를 최종 서버의 MAC 주소라고 항상 생각하면 안 된다.

슬라이드의 프레임 예시는 Ethernet을 사용한다. 모든 링크 기술의 상세 프레임 구조가 Ethernet과 완전히 같다는 뜻은 아니다.

### 5.7 1계층 — Physical Layer, 물리 계층

- 자료의 핵심 표현: 케이블 등으로 신호 변환 전송.
- 기능 관점의 해설: 비트열을 실제 매체에서 전달 가능한 신호로 표현하고 송수신.
- 기본 단위 표기: Bit 또는 Bits.

위 계층에서 만든 정보는 실제로 전기적·광학적·무선 신호 등으로 전달되어야 한다. 이 계층의 관점은 웹 요청의 의미나 목적지 응용 프로그램이 아니라 신호를 보내고 받는 것이다.

**헷갈림 방지:** Bit는 논리적인 0과 1이다. 비트와 실제 신호의 관계를 0은 항상 특정 전압, 1은 항상 다른 특정 전압이라고 고정해서 이해하지 않는다. 구체적인 표현 방식은 전송 기술에 따라 달라진다.

### 5.8 아래에서 위로 다시 말하기

```text
1 Physical      : 신호로 비트를 전달
2 Data Link     : 현재 링크에서 프레임을 전달
3 Network       : IP 기반으로 네트워크 간 패킷을 전달
4 Transport     : 응용 프로그램 사이의 전송 서비스를 제공
5 Session       : 대화 관계를 관리
6 Presentation  : 데이터 표현을 맞춤
7 Application   : 네트워크 서비스의 메시지와 의미를 처리
```

이 순서는 계층 번호 순서다. 송신 캡슐화는 반대로 위에서 아래로 진행한다.

## 6. TCP/IP 4계층과 OSI의 대응

**자료: p.7~8, p.11**

이 강의의 TCP/IP 모델은 **4계층** 이다.

```text
OSI                                      TCP/IP
7 Application    ┐
6 Presentation   ├────────────────────── Application
5 Session        ┘
4 Transport       ────────────────────── Transport
3 Network         ────────────────────── Internet
2 Data Link      ┐
1 Physical       ┴────────────────────── Network Interface
```

### 6.1 Application

OSI 상위 세 계층에 해당하는 기능을 큰 범주로 묶는다. 응용 서비스의 교환 규칙과 그에 필요한 표현·대화 관리 기능을 함께 생각한다.

### 6.2 Transport

OSI Transport와 큰 역할이 대응한다. 응용 프로그램 간 전송 서비스가 핵심이며 TCP와 UDP가 대표적으로 연결된다. 두 모델에서 이름이 같다고 하여 모든 구현 세부 사항까지 일대일로 같다는 뜻은 아니다.

### 6.3 Internet

OSI Network에 대응한다. IP 기반의 네트워크 간 전달을 중심으로 이해한다. p.7 그림에는 `Network`라는 표기도 있지만, p.11의 4계층 목록은 `Internet`을 사용한다.

### 6.4 Network Interface

OSI Data Link와 Physical에 해당하는 기능을 묶는다. 1장에서는 Network Access, 다른 그림에서는 Link로 표시되기도 한다. 이 문서에서는 같은 4계층 모델의 하위 영역을 가리키는 표현으로 읽는다.

### 6.5 왜 모델이 두 개인가?

OSI는 기능을 세분해 설명하는 참조 모델이고, TCP/IP는 인터넷 통신을 설명하는 실용적인 프로토콜 구조와 연결된다. 실제 장치가 OSI 모델을 버리고 TCP/IP 모델로 ‘모드를 전환’하는 것은 아니다. 하나의 통신을 서로 다른 분류 틀로 살펴보는 것이다.

다른 교재에서는 링크와 물리를 분리한 5계층 모델도 볼 수 있다. 그러나 이 자료의 계층 수를 묻는 문제에서는 **TCP/IP 4계층** 을 기준으로 답한다.

## 7. PDU: Data·Segment·Packet·Frame·Bit

### 7.1 PDU란 무엇인가?

**자료: p.7~10**

**PDU(Protocol Data Unit)** 는 특정 계층의 프로토콜이 처리하는 데이터 단위다. 하나의 사용자 데이터라도 어느 계층에서 보느냐에 따라 포함된 제어 정보와 부르는 이름이 달라진다.

자료의 기본 흐름은 다음과 같다.

```text
상위 계층    Data
전송 계층    Segment
네트워크     Packet
데이터 링크  Frame
물리         Bit
```

이 다섯 단어는 같은 내용을 단순히 다르게 부르는 것만은 아니다. 내려가면서 해당 계층의 정보가 추가되어 **상위 단위를 포함하는 더 큰 단위** 가 된다.

### 7.2 Data — 실제 전달할 내용

p.7에서는 Data 옆에 ‘실제 내용’이라고 적혀 있다. 예를 들어 응용이 전달하려는 요청 메시지나 파일의 일부가 해당한다.

다만 p.9에는 Application Header도 나타난다. 즉 ‘Data에는 어떤 헤더도 없다’고 단정할 수 없다. 전송 계층에서 보는 Data 안에는 응용 프로토콜이 만든 제어 정보가 포함될 수 있다.

### 7.3 Segment — 어떤 응용 통신인가?

p.7의 표현은 ‘누구에게 줄 거야? (port)’다. 전송 계층이 상위 데이터를 받아 자신의 제어 정보를 추가한 단위로 이해한다.

**명칭 주의:** Segment는 TCP의 PDU를 설명할 때 쓰는 이름이다. UDP의 단위는 보통 **Datagram** 이라고 부른다. 자료의 기본 암기 흐름은 Segment를 사용하지만, p.10 오른쪽 UDP 그림까지 모두 TCP Segment라고 부르면 안 된다.

### 7.4 Packet — 어느 네트워크 목적지로 가는가?

p.7에서는 ‘어느 집으로? (IP 주소)’라는 비유를 쓴다. IP 헤더를 포함해 네트워크 간 전달에 필요한 정보를 갖춘 단위다.

주소 비유의 핵심은 목적지를 구분한다는 점이다. IP 주소가 실제 건물 주소처럼 영구적으로 고정된다는 뜻은 아니다.

### 7.5 Frame — 현재 링크에서 어떻게 전달하는가?

p.7에서는 ‘어느 길로 갈 건데? (MAC 주소)’라는 비유를 쓴다. 이 문구는 **현재 링크의 전달 대상** 을 떠올리는 보조 표현으로 이해하는 것이 정확하다. MAC 주소 자체가 전체 인터넷 경로를 지정하는 것은 아니다.

Frame은 Packet에 링크 계층의 헤더, 그리고 Ethernet 예시에서는 Trailer를 더한 형태다. Trailer에는 오류 검출에 사용하는 FCS 같은 정보가 들어갈 수 있다.

### 7.6 Bit — 매체로 전달되는 비트열

Frame을 이루는 정보는 비트열로 표현되어 매체를 통해 전달된다. 여기서는 데이터 단위의 포장 관계에서 실제 신호 전달로 넘어간다.

**정리:** Port는 응용 통신 대상, IP 주소는 네트워크의 목적지, MAC 주소는 링크의 전달 대상이라는 구분이 PDU의 계층 구분과 함께 연결된다.

## 8. PDU Flow 1: 캡슐화와 역캡슐화

**자료: p.9**

### 8.1 캡슐화의 의미

**Encapsulation(캡슐화)** 은 상위 계층에서 받은 단위를 아래 계층이 자신의 데이터 부분으로 포함하고, 필요한 제어 정보를 덧붙이는 과정이다.

- **Header(헤더):** 해당 프로토콜의 제어 정보를 담는 앞부분.
- **Payload(페이로드):** 그 계층이 운반하는 내용. 상위 계층의 PDU가 될 수 있다.
- **Trailer(트레일러):** 일부 프로토콜이 뒤에 붙이는 제어 정보.

다음 도식은 p.9의 TCP·IP·Ethernet 예시를 일반적인 논리적 배치로 다시 쓴 것이다. 필드 크기나 실제 전송 시점까지 나타내지는 않는다.

```text
응용 데이터
[ Application Data ]

TCP Segment
[ TCP Header | Application Data ]

IP Packet
[ IP Header | TCP Header | Application Data ]

Ethernet Frame
[ Ethernet Header | IP Header | TCP Header | Application Data | Trailer ]

물리적 전달
위 프레임을 이루는 비트열 → 매체에 맞는 신호
```

### 8.2 송신 과정을 단계별로 따라가기

1. **응용 계층:** 사용자에게서 받은 내용으로 응용 프로토콜 데이터를 만든다. p.9에는 User Data 앞에 APP Header가 추가되는 모습도 나온다.
2. **전송 계층:** 응용 데이터를 포함하고 TCP 헤더를 붙인다. 결과가 TCP Segment다.
3. **Internet 계층:** Segment를 포함하고 IP 헤더를 붙인다. 결과가 IP Packet이다.
4. **링크 계층:** Packet을 포함하고 Ethernet 헤더와 Trailer를 붙인다. 결과가 Frame이다.
5. **물리 계층:** Frame의 정보를 비트열과 신호로 전달한다.

이때 아래 계층은 위 계층이 붙인 헤더를 원칙적으로 자기 Payload의 일부로 취급할 수 있다. 예를 들어 IP 계층에서 Payload에는 TCP 헤더와 응용 데이터가 함께 들어 있다.

### 8.3 왜 여러 번 포장하는가?

각 계층이 해결하는 문제가 다르기 때문이다.

- 응용 프로토콜은 요청의 의미를 표현한다.
- TCP는 전송 서비스에 필요한 정보를 담는다.
- IP는 네트워크 간 전달에 필요한 정보를 담는다.
- Ethernet은 현재 링크의 전달에 필요한 정보를 담는다.

하나의 헤더로 모든 기능을 섞지 않고 역할별로 구분하기 때문에, 같은 상위 데이터가 다른 링크 기술 위에서도 전달될 수 있다.

### 8.4 수신 측의 역캡슐화

**Decapsulation(역캡슐화)** 은 각 계층이 자신에게 해당하는 정보를 처리하고, 내부 데이터를 위 계층으로 넘기는 과정이다.

```text
수신 신호와 비트열
    ↑
Frame 처리: 링크 계층 정보 확인 → 내부 Packet
    ↑
Packet 처리: IP 정보 확인 → 내부 Segment
    ↑
Segment 처리: TCP 정보 처리 → 응용 Data
    ↑
응용 프로토콜 해석 → 사용자에게 의미 있는 결과
```

‘헤더 제거’는 데이터 구조를 설명하는 표현이다. 실제 구현이 반드시 메모리에서 매번 바이트를 지우는 방식이라는 뜻은 아니다. 또한 역캡슐화는 그냥 포장을 벗기는 것만이 아니라 **제어 정보를 확인하고 프로토콜 규칙에 맞게 처리하는 과정** 이다.

### 8.5 중간 장비도 응용 계층까지 모두 올라가는가?

**보충 설명:** 보통의 중계 동작에서 모든 장비가 사용자 데이터를 응용 계층까지 해석하는 것은 아니다. 예를 들어 라우터는 들어온 링크의 프레임을 처리하고 IP 패킷을 다음 링크로 전달하며, 다음 링크에 맞는 프레임을 만든다.

```text
호스트 A → 링크 1의 Frame → 라우터 → 링크 2의 Frame → 호스트 B
             Packet 포함             Packet 포함
```

따라서 링크별 Frame이 끝까지 동일하다고 보면 안 된다. IP 패킷도 전달 과정에서 일부 필드가 바뀔 수 있으므로 ‘어떤 비트도 변하지 않는다’고 일반화하지 않는다. 이 장에서는 **종단 간 전달과 한 링크의 전달을 구분한다** 는 핵심만 잡는다.

## 9. PDU Flow 2: 그림 속 포함 관계 읽기

**자료: p.10**

### 9.1 왼쪽 누적 블록 그림

왼쪽 그림은 Data에 L4 Header, L3 Header, L2 Header와 L2 Trailer가 누적되는 모습을 보여 준다.

- L4: Layer 4, 전송 계층.
- L3: Layer 3, 네트워크 계층.
- L2: Layer 2, 데이터 링크 계층.

그림은 블록을 시각적으로 쌓는 방식으로 그려져 있어 Header가 Data 오른쪽에 보인다. 이것을 그대로 실제 프레임의 바이트 순서로 암기하지 않는다. 중요한 것은 **각 단계가 이전 단위 전체를 포함한다** 는 점이다.

```text
Segment = L4 제어 정보 + 상위 데이터
Packet  = L3 제어 정보 + Segment
Frame   = L2 제어 정보 + Packet + 필요 시 L2 Trailer
```

### 9.2 오른쪽 UDP·IP·Frame 그림

오른쪽 그림은 Application의 Data 아래에 UDP Header와 UDP Data, 그 아래 IP Header와 IP Data, 마지막으로 Frame Header·Frame Data·Frame Footer를 보여 준다.

여기서 **Data라는 말은 계층에 따라 가리키는 범위가 달라진다.**

- UDP Data는 응용 데이터를 담는다.
- IP Data는 UDP 헤더와 UDP 데이터를 함께 담는다.
- Frame Data는 IP 헤더와 IP 데이터를 함께 담는다.

따라서 ‘데이터’라는 단어를 볼 때는 항상 **어느 계층이 보는 데이터인가** 를 먼저 확인해야 한다.

### 9.3 크기로 이해하는 포함 관계

**보충 예시 — 계산 이해용 가정이며 실제 헤더 크기를 제시하는 것이 아니다.**

응용 데이터 크기를 `D`, 각 헤더 크기를 `H4`, `H3`, `H2`, 링크 Trailer 크기를 `T2`라고 하자. 분할·패딩 등은 제외한다.

```text
Segment 크기 = D + H4
Packet 크기  = D + H4 + H3
Frame 크기   = D + H4 + H3 + H2 + T2
```

여기서 Frame이 Segment보다 더 많은 계층 정보를 포함한다는 사실을 확인할 수 있다. 실제 전송에서는 프로토콜별 제한과 추가 필드 등이 있으므로 이 식을 모든 경우의 정확한 길이 공식으로 사용하지 않는다.

## 10. 강의자료 확인 문제와 해설

**자료: p.11. 정답과 이유는 개념에 근거한 해설이다.**

### 10.1 네트워크 모델에 대한 네 문장

**문장 1. OSI 7계층 모델은 네트워크 통신 과정을 7단계로 나눠 설명한다.**

맞다. 단, 시간순으로 반드시 일곱 번의 독립 행사가 발생한다는 뜻보다 기능을 일곱 계층으로 구분한다는 뜻에 가깝다.

**문장 2. TCP/IP 모델은 OSI보다 단순화한 4계층이다.**

이 강의의 모델 기준으로 맞다. OSI의 상위 세 계층과 하위 두 계층을 각각 큰 범주로 묶어 대응시킨다. 두 모델의 역사적 관계까지 ‘OSI를 그대로 줄여 TCP/IP를 만들었다’고 이해하지 않는다.

**문장 3. 두 모델의 Transport Layer는 역할이 같다.**

이 자료의 비교 수준에서는 맞다. 양 끝 응용 사이의 전송 기능이라는 큰 역할이 대응한다.

**문장 4. TCP/IP는 인터넷 통신을 설명하는 실용적 모델이다.**

맞다. 인터넷에서 쓰이는 프로토콜 구조와 연결해 이해한다.

### 10.2 True/False 1 — 계층 이름

**문제 요지:** OSI는 Physical, Data Link, Network, Transport, Session, Presentation, Application으로 구성되고, TCP/IP는 Network Interface, Internet, Transport, Application으로 구성된다.

**정답: True.**

둘 다 아래에서 위로 나열한 것이다. TCP/IP의 Network Interface가 OSI의 Physical과 Data Link를 묶고, TCP/IP의 Application이 OSI 상위 세 계층에 대응한다.

### 10.3 True/False 2 — 캡슐화 순서

**문제 요지:** 출발지 컴퓨터의 데이터를 `Segment → Frame → Packet` 순서로 캡슐화한다.

**정답: False.**

올바른 기본 흐름은 다음과 같다.

```text
Data → Segment → Packet → Frame → Bit
```

Frame은 Packet을 내부에 담으므로 Packet보다 먼저 만들어지는 것으로 설명하면 포함 관계가 뒤집힌다.

**서술형 답안 예시:** 전송 계층에서 상위 데이터를 포함하는 Segment를 만들고, 네트워크 계층에서 IP 정보를 추가해 Packet을 만든다. 링크 계층에서는 Packet에 링크 정보를 추가해 Frame을 만들며, 이를 물리적으로 전송한다.

## 11. 헷갈리기 쉬운 포인트와 시험 대비

### 11.1 자주 틀리는 문장 교정

- “케이블만 연결하면 통신이 완성된다.” → 인터페이스와 프로토콜 등도 맞아야 한다.
- “Wi-Fi 비밀번호도 네트워크에 필요한 것이므로 Node다.” → 필요한 정보와 통신 주체는 다르다.
- “MAC 주소가 인터넷 전체 경로를 결정한다.” → 링크의 전달 대상과 IP 기반 경로 선택을 구분한다.
- “상위 PDU는 아래 계층으로 가면서 사라진다.” → 일반적인 캡슐화에서는 아래 PDU의 Payload로 포함된다.
- “Header는 어디서나 Payload 바깥에 있다.” → TCP Header는 TCP 관점의 헤더이지만 IP 관점에서는 Payload에 포함된다.
- “Transport는 무조건 신뢰성을 보장한다.” → TCP와 UDP의 제공 기능을 구분한다.
- “UDP의 PDU도 정확히 TCP Segment다.” → UDP Datagram이라는 명칭을 구분한다.
- “역캡슐화는 암호를 푸는 것이다.” → 계층 제어 정보를 처리해 위로 전달하는 과정이며 암호 해독과 동의어가 아니다.
- “계층 대응선은 실제 전선이다.” → 같은 계층의 논리적 관계를 표현한 것이다.

### 11.2 자체 점검 문제

**문제 1.** 스마트폰·광케이블·TCP/IP를 세 요소에 대응시키고 한 문장으로 연결하라.

**답:** 스마트폰은 Node, 광케이블은 Link를 구성하는 전송 매체의 예, TCP/IP는 Protocol 모음의 예다. 노드가 링크를 통해 프로토콜에 따라 데이터를 주고받는다.

**문제 2.** 목적지 컴퓨터가 같은데 Port가 다른 두 통신을 구분하는 계층은?

**답:** 전송 계층. Port를 사용해 응용 통신 대상을 구분한다.

**문제 3.** TCP Segment는 IP Packet의 어디에 들어가는가?

**답:** IP Payload에 들어간다. 이때 TCP 헤더도 IP Payload의 일부다.

**문제 4.** 한 Frame 안에서 IP Header와 TCP Header를 함께 발견하는 것이 가능한가?

**답:** 가능하다. Ethernet 위에서 IP와 TCP를 사용하는 예에서는 Frame 안에 IP Packet이, 그 안에 TCP Segment가 들어 있다.

**문제 5.** 수신 시 `Frame → Packet → Segment → Data`는 무슨 과정인가?

**답:** 역캡슐화다. 각 계층의 정보를 확인하고 내부 데이터를 상위 계층에 전달한다.

**문제 6.** 응용 데이터 100단위, L4 헤더 10단위, L3 헤더 20단위, L2 헤더 5단위, Trailer 5단위일 때 단순화한 Frame 크기는?

**답:** `100 + 10 + 20 + 5 + 5 = 140단위`. 모두 학습용 가정값이며 실제 프로토콜 크기와 무관하다.

**문제 7.** “TCP/IP의 Application은 OSI의 Application에만 대응한다.” — OX

**답: X.** 자료의 대응에서는 Session, Presentation, Application의 세 계층에 해당하는 기능을 묶는다.

### 11.3 시험 직전 암기와 이해의 구분

**암기할 것:** 세 요소의 이름, OSI 순서, TCP/IP 4계층, PDU 순서, 역사 인물의 연결.

**설명할 것:** 계층화의 이유, Port/IP/MAC의 차이, 캡슐화의 포함 관계, 동일 계층의 논리적 관계와 실제 이동의 차이, TCP와 UDP 때문에 생기는 일반화의 한계.

순서만 외웠다면 “왜 Frame 다음에 Packet이 아니라 Packet 다음에 Frame인가?”라는 질문에 답해 본다. **Frame이 Packet을 담기 때문** 이라고 말할 수 있어야 한다.

## 12. 장 마지막 총정리

네트워크에는 **Node·Link·Protocol** 이 필요하다. 노드가 통신의 주체이고 링크가 통로이며 프로토콜이 해석과 교환의 규칙이다.

이 통신의 기능을 구분하는 틀이 OSI와 TCP/IP다. OSI는 7계층으로 역할을 자세히 나누고, 이 강의의 TCP/IP 모델은 4계층으로 인터넷 통신 구조를 설명한다.

사용자 데이터는 송신 측에서 계층별 제어 정보를 얻으며 내려간다.

```text
Data
  → Segment: 전송 계층 정보, Port
  → Packet: 네트워크 계층 정보, IP
  → Frame: 링크 계층 정보, MAC 등
  → Bit/Signal: 매체를 통한 실제 전달
```

수신 측은 각 계층의 정보를 처리하며 반대 방향으로 올라간다. 이 과정의 핵심은 **이름의 변경보다 포함 관계와 역할의 추가** 다.
