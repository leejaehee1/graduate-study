## 1. 학습 목표와 2장과의 연결

### 1.1 서로 다른 두 종류의 ‘3요소’

**자료: p.2~3**

2장과 3장은 모두 세 요소를 소개하지만 같은 목록은 아니다.

- 2장: **Node·Link·Protocol** — 네트워크를 구성하는 주체, 통로, 규칙.
- 3장: **Interface·Protocol·Standardization** — 서로 다른 시스템을 연결하고 함께 동작시키는 접점, 규칙, 공통 규격.

서로 모순되는 정의가 아니라 설명하는 관점이 다르다. 2장은 “무엇으로 이루어지는가?”, 3장은 “다른 시스템들이 어떻게 연동할 수 있는가?”를 묻는다.

```text
Node ───────── Link ───────── Node
  │                             │
Interface                   Interface
  └──── 공통 Protocol을 따름 ────┘
       공통 규격을 정하는 Standardization
       그 결과로 추구하는 Interoperability
```

### 1.2 Key Summary의 스마트 교통 그림

p.3의 그림에는 교통 운영 시스템, 실시간 데이터, 긴급 차량 모니터링, 스마트 횡단보도, 스마트 교차로, 돌발 상황 감지, 신호 최적화, 교통 정책 지원 등이 연결되어 있다.

그림을 다음과 같이 읽으면 세 요소가 연결된다.

1. 여러 장치와 시스템이 관찰한 정보를 교환해야 한다.
2. 정보를 주고받는 접점이 필요하므로 Interface가 중요하다.
3. 관찰값이나 제어 메시지의 뜻을 함께 이해해야 하므로 Protocol이 필요하다.
4. 서로 다른 장비도 함께 동작해야 하므로 공통 규격이 필요하다.

**보충 예시:** 어떤 장치의 ‘1’이 긴급 차량 감지를 뜻하는데 수신 시스템이 정상 상태로 해석한다면, 데이터가 도착해도 올바른 연동은 아니다. 그림은 단순한 연결 수보다 **정보를 같은 의미로 해석하고 동작하는 것** 의 중요성을 보여 주는 사례로 이해할 수 있다. 실제 교통 프로토콜이나 메시지 형식이 슬라이드에 제시된 것은 아니다.

### 1.3 이 장에서 설명할 수 있어야 하는 것

- Interface, Protocol, Standardization의 차이와 연결.
- Interoperability의 의미와 표준화의 목적.
- ISO, IEEE, IETF의 기본 역할.
- 물리적 인터페이스와 논리적 인터페이스의 예.
- System, Transmission Media, Internet, Network, Node, Gateway, DNS의 구분.
- System OX 3문항과 Review 6문항의 정답 근거.

## 2. Interface: 연결하고 기능을 이용하는 접점

**자료: p.4, 구체적인 분류는 p.7**

**Interface(인터페이스)** 는 서로 다른 대상이 접촉하거나 기능·데이터를 주고받는 경계와 그 이용 방식이다. 네트워크에서는 장치나 소프트웨어 사이의 연결을 가능하게 하는 접점과 규격으로 이해한다.

### 2.1 하드웨어 관점과 소프트웨어 관점

p.4는 하드웨어 관점 옆에 마우스를, 소프트웨어 관점 옆에 명령 화면·그래픽 화면·터치 화면을 배치한다.

- 마우스는 사람이 컴퓨터에 입력을 전달하는 물리적 접점의 예다.
- 명령·그래픽·터치 화면은 사용자가 소프트웨어와 상호작용하는 방식의 차이를 보여 준다.

이 그림은 먼저 넓은 의미의 인터페이스를 일상적인 예로 소개한다. 네트워크에서 말하는 인터페이스를 ‘화면 디자인’으로만 이해하지 않도록, p.7의 RJ-45·광 커넥터·Socket·API 예시로 이어 읽어야 한다.

### 2.2 연결 규격이 필요한 이유

**보충 설명:** 두 장치를 연결하려면 꽂을 수 있다는 사실뿐 아니라 신호와 데이터 교환에 필요한 조건이 맞아야 한다. 소프트웨어에서도 호출 이름만 아는 것으로는 부족하며 어떤 입력을 주고 어떤 결과를 받는지 알아야 한다.

따라서 인터페이스는 단순히 두 대상 사이에 ‘무언가가 있다’는 뜻이 아니라, **서로 만나는 경계에서 어떻게 이용할 수 있는지를 정하는 것** 과 관련된다.

### 2.3 물리적 인터페이스와 논리적 인터페이스

**자료: p.7**

**물리적 인터페이스(Physical Interface)** 는 실제 장치 연결의 접점과 관련된다.

- 자료의 예: RJ-45 단자, 광 커넥터.
- 관찰할 대상: 연결부의 형태와 해당 연결에 필요한 물리적 조건.

**논리적 인터페이스(Logical Interface)** 는 소프트웨어가 기능이나 통신 서비스를 이용하는 약속된 접점과 관련된다.

- 자료의 예: Socket, API.
- **Socket:** 응용 프로그램이 네트워크 통신을 수행할 때 이용하는 소프트웨어적 통신 접점으로 이해한다.
- **API(Application Programming Interface):** 프로그램이 다른 소프트웨어 기능을 호출하고 사용하는 방법을 정의한 접점이다.

**보충 예시:** 프로그램이 Socket API를 이용해 운영체제에 데이터 전송을 요청하면, 실제 신호 전달은 아래쪽 네트워크 기능과 장치가 담당한다. 소프트웨어 접점과 물리적 접점은 하나의 통신 안에서 함께 필요할 수 있다.

### 2.4 API와 Protocol을 혼동하지 않기

API는 소프트웨어 기능을 **어떻게 호출해 이용하는가** 를 설명하고, 통신 프로토콜은 상대와 메시지를 **어떤 규칙으로 교환하는가** 를 설명한다.

예를 들어 데이터 전송 함수를 호출하는 방법과, 상대가 해석할 메시지의 형식·순서는 다른 층위의 약속이다. 둘 다 규칙이 있다는 이유만으로 같은 개념으로 취급하지 않는다.

## 3. Protocol: 데이터를 교환하는 대화 규칙

**자료: p.5**

자료는 시스템이 전송 매체를 통해 데이터를 교환할 때 따르는 표준화된 대화 규칙으로 Protocol을 설명한다.

### 3.1 송신자·수신자 그림의 의미

왼쪽 그림에는 Sender, Receiver, Transmission Media, Message와 양쪽의 Protocol(Rules)이 있다.

```text
송신 시스템                            수신 시스템
Protocol 규칙                         Protocol 규칙
     │                                    │
     └──── Message / Transmission Media ──┘
```

매체는 데이터를 전달하는 통로이고, 프로토콜은 그 데이터를 생성·해석하고 반응하는 규칙이다. 통로가 같다고 메시지의 의미가 자동으로 맞는 것은 아니다.

오른쪽 그림은 여러 기기가 통신 규칙을 통해 연결되는 모습을 보여 준다. 그림에는 TCP/IP, HTTP, FTP, POP, SMTP, IPX/SPX 등의 이름이 보인다. 이 페이지의 핵심은 각 프로토콜의 세부 암기보다 **여러 수준의 통신에 서로 다른 규칙이 존재한다** 는 점이다. 이 목록이 현재 모든 네트워크에서 동일하게 쓰이는 필수 목록이라는 뜻은 아니다.

### 3.2 일상 대화 비유를 더 정확하게 이해하기

프로토콜을 공통 언어에 비유하면 이해하기 쉽다. 다만 실제 통신 규칙에는 다음과 같은 내용도 포함될 수 있다.

- 메시지의 항목과 길이 등 형식.
- 각 항목이 뜻하는 바.
- 요청과 응답의 순서.
- 예상한 응답이 없거나 오류가 생겼을 때의 처리.

**학습용 가상 예시:** 한쪽이 `TEMP:25`를 보내고 상대가 이를 온도 25도로 해석하도록 약속했다고 하자. 상대가 같은 문자열을 다른 단위나 다른 상태 정보로 해석하면 올바른 교환이 아니다. 이 예는 실제 표준 프로토콜이 아니라 형식과 의미가 함께 맞아야 함을 보여 주기 위한 것이다.

### 3.3 2장의 계층 모델과 연결

프로토콜은 하나만 있는 것이 아니다. 서비스 의미를 다루는 규칙, 전송 서비스를 다루는 규칙, IP 전달 규칙, 링크의 프레임 규칙이 함께 사용된다.

2장에서 각 계층에 헤더가 추가된 이유는 이 규칙을 수행하는 데 필요한 정보를 담아야 하기 때문이다. 따라서 **계층·프로토콜·헤더·PDU** 는 서로 따로 외울 개념이 아니라 하나의 통신을 서로 다른 관점에서 설명하는 말이다.

## 4. Standardization: 함께 동작하기 위한 공통 규격

**자료: p.6. 슬라이드 제목의 `Standardzation`은 `Standardization`의 오기로 보고 정리한다.**

**Standardization(표준화)** 은 서로 다른 시스템이 상호 연동하여 동작할 수 있도록 공통 형식과 규격을 정하는 과정이다.

### 4.1 왜 개별 약속만으로는 부족한가?

두 제조사가 둘만의 규칙을 합의하면 두 제품은 통신할 수 있다. 그러나 제조사와 제품이 많아질수록 각 조합마다 별도 연결 방식을 만들면 복잡해진다. 공통 규격이 있으면 여러 구현이 같은 기준을 목표로 개발될 수 있다.

이 때문에 표준화는 네트워크를 특정 제조사의 제품 조합에서 더 넓은 생태계로 확장하는 데 중요하다.

### 4.2 프린터와 맞물린 톱니 그림의 의미

p.6에는 프린터와 `standard / process` 톱니 그림이 나온다. 프린터는 다른 시스템이 장치의 기능을 이용해야 한다는 익숙한 사례이고, 톱니는 서로 맞는 형식이 있어야 함께 작동한다는 비유로 읽을 수 있다.

슬라이드는 특정 프린터 프로토콜이나 모든 프린터의 완전한 호환성을 설명하지 않는다. **서로 다른 구현 사이에 공통 규격이 필요하다** 는 핵심을 가져간다.

### 4.3 Protocol과 Standardization의 차이

- **Protocol:** 실제 교환할 때 따르는 규칙의 내용.
- **Standardization:** 여러 시스템이 공통으로 따를 규격을 정하고 맞추는 과정.

모든 프로토콜이 반드시 공개 국제표준인 것은 아니다. 강의자료는 표준화된 프로토콜을 통한 연동에 초점을 맞추지만, 특정 조직 내부의 독자 규칙도 프로토콜일 수 있다. 중요한 것은 **규칙이 존재한다는 것과 널리 합의된 표준이라는 것의 구분** 이다.

## 5. Recommended Additions: 상호 운용성과 표준화 기구

**자료: p.7**

### 5.1 Interoperability — 상호 운용성

**Interoperability(상호 운용성)** 는 서로 다른 제조사의 장비나 운영체제 등이 정보를 교환하고 그 정보를 이용하여 함께 동작할 수 있는 성질이다.

단순히 연결 케이블이 맞거나 신호가 도착하는 수준을 넘어, 교환한 내용을 해석하여 기대한 기능을 수행하는 것까지 연결된다.

```text
공통 규격 마련: Standardization
    ↓
각 시스템의 규격 구현: Interface와 Protocol 구현
    ↓
실제 환경에서 연동: Interoperability
```

**보충 설명:** 표준을 따른다는 사실은 연동의 중요한 기반이지만 실제 구현 오류, 설정, 지원 기능의 차이 때문에 문제가 생길 수도 있다. ‘같은 표준 이름이 적혀 있으면 어떤 조건에서도 반드시 통신된다’는 절대 명제로 확대하지 않는다.

### 5.2 ISO

**ISO(International Organization for Standardization)** 는 국제표준화기구다. 이 과목에서는 특히 OSI 참조 모델과 연결해 기억한다.

핵심 연결: **ISO → OSI 모델을 통한 통신 기능의 체계적 설명.** ISO와 OSI는 글자가 비슷하지만 하나는 기구, 하나는 모델 이름이다.

### 5.3 IEEE

**IEEE(Institute of Electrical and Electronics Engineers)** 는 전기·전자·컴퓨터 분야의 전문 기구이며 표준화 활동을 한다. 네트워크에서는 IEEE 802 계열과 연결해 이해하면 된다.

**보충 대표 예시:** Ethernet과 관련된 IEEE 802.3, 무선 LAN과 관련된 IEEE 802.11. 이 예시는 기구와 실제 네트워크 기술을 연결하기 위한 것이며 세부 버전·속도 암기까지 확장하지 않는다.

### 5.4 IETF와 RFC

**IETF(Internet Engineering Task Force)** 는 인터넷 기술의 표준화와 관련된 기구다. 자료는 IETF 옆에 ‘RFC 표준’이라고 표시한다.

**RFC(Request for Comments)** 는 인터넷 기술과 관련된 문서를 발행하는 시리즈다. 인터넷 표준 문서도 RFC로 발행되지만, **모든 RFC가 인터넷 표준은 아니다.** 정보 제공, 실험 등 다른 지위의 RFC도 있다. 이 구분은 자료의 축약 표현을 정확하게 이해하기 위한 보충이다. [IETF의 RFC 설명](https://www.ietf.org/process/rfcs/)

### 5.5 기구 이름과 네트워크 소유권을 구분하기

표준을 정하는 활동과 인터넷 전체를 소유하는 것은 다르다. ISO·IEEE·IETF가 등장한다고 해서 이들 중 하나가 모든 인터넷 장비와 회선을 소유한다는 뜻은 아니다. 이는 뒤의 Review Q4와 연결된다.

## 6. System과 Transmission Media

### 6.1 System — 통신에 참여하는 전체 구성

**자료: p.8**

네트워크에서 **System(시스템)** 은 역할을 수행하는 구성 요소들의 전체로 이해한다. 하드웨어만이 아니라 통신에 필요한 소프트웨어와 프로토콜 구현도 고려해야 한다.

그림에는 데스크톱, 키오스크, 차량 내부 시스템, Windows 화면이 함께 나온다. 시스템의 형태가 PC로 제한되지 않으며 운영체제·소프트웨어 측면도 중요하다는 점을 보여 준다.

**보충 예시:** 네트워크 키오스크는 화면과 본체만으로 서비스를 완성하지 않는다. 요청을 만드는 프로그램, 통신을 지원하는 운영체제 기능, 실제 송수신 장치 등이 함께 동작해야 한다.

### 6.2 System OX 3문항

**문항 1. 시스템은 단독으로 작동하는 하드웨어만 의미하고, 통신 소프트웨어나 프로토콜은 포함되지 않는다.**

**정답: False.** 통신 기능을 수행하는 시스템을 하드웨어에만 한정할 수 없다. 프로토콜 규칙을 구현하는 소프트웨어도 시스템 동작에 포함된다.

**문항 2. 두 시스템을 전송 매체로 연결하면 별도의 Interface 규격 없이 데이터 교환이 완성된다.**

**정답: False.** 매체는 전달 통로일 뿐이다. 연결을 이용하는 인터페이스와 데이터를 해석하는 규칙이 맞아야 한다.

**문항 3. 다른 제조사의 시스템도 동일한 통신 프로토콜을 구현하고 표준화를 준수하면 상호 연동할 수 있다.**

**정답: True.** 이 문항은 표준화와 상호 운용성의 관계를 묻는다. ‘할 수 있다’는 원리 설명이지 구현·설정의 문제까지 모두 사라진다는 뜻은 아니다.

### 6.3 Transmission Media — 신호가 지나가는 매체

**자료: p.9**

**Transmission Media(전송 매체)** 는 시스템 사이에서 신호가 실제로 전달되는 물리적 경로나 환경이다.

- 유선 매체: 구리선 기반 케이블, 광섬유 등.
- 무선 전달: 전자기파가 공간을 통해 전달되는 방식.

**자료 표현 주의:** p.9에는 ‘시스템 간의 물리적인 연동을 위한 논리적인 규격’이라는 문장이 적혀 있다. 이 표현은 전송 매체 자체의 정의로 사용하기에는 부정확하다. **매체는 신호 전달 통로이고, 규격은 그 통로를 연결·이용하는 조건** 으로 구분해서 학습한다.

### 6.4 케이블·Wi-Fi·Category 표 그림 읽기

p.9에는 랜 케이블 사진, Wi-Fi 로고, 케이블 Category별 표가 나온다. 표는 CAT.1~CAT.8 등의 구분과 전송 속도·대역폭·규격을 병렬로 보여 준다.

이 그림에서 가져갈 학습 포인트는 다음과 같다.

1. 전송 매체와 연결 기술에는 여러 종류가 있다.
2. 케이블은 겉보기에 비슷해도 분류와 지원 조건이 다를 수 있다.
3. **전송 속도(bps)** 와 **주파수 대역폭(Hz)** 은 다른 양이다.
4. 연결부의 모양만 보고 실제 통신 성능을 확정할 수 없다.

**자료 범위와 정확성:** 표에는 CAT.6e 같은 명칭과 조건이 생략된 속도 값이 포함되어 있어 모든 셀을 그대로 표준 보장 성능으로 암기하기보다 분류의 의미를 이해한다. 이 노트에서는 해당 표를 별도의 최신 표준 규격표로 재작성하지 않는다. 실제 지원 속도에는 길이, 장비, 적용 표준 등의 조건이 관련되며 상세 케이블 규격 검증은 이 장의 범위를 벗어난다.

Wi-Fi는 케이블과 같은 물체의 이름이 아니라 무선 네트워크 기술이다. 이 페이지에서는 **유선뿐 아니라 무선도 연결 방법에 포함된다** 는 의미로 이해한다.

### 6.5 Link·Media·Interface의 구분

- Link: 노드 사이의 연결 관계 또는 통로라는 관점.
- Transmission Media: 신호를 실제 전달하는 매체라는 관점.
- Interface: 시스템이 그 연결을 이용하는 접점과 이용 방식이라는 관점.

예를 들어 랜 케이블은 매체, 연결 단자는 물리적 인터페이스의 예, 두 장치 사이 연결은 링크로 설명할 수 있다. 같은 통신 상황의 서로 다른 측면을 가리키는 것이다.

## 7. Internet과 Network

**자료: p.10**

### 7.1 Internet

자료는 인터넷을 네트워크들이 유기적으로 연결되어 동작하는 통합 네트워크로 설명한다.

**Internet(인터넷)** 은 여러 네트워크가 연결되어 공통 인터넷 프로토콜을 기반으로 통신하는 세계적인 네트워크 체계로 이해한다. 흔히 ‘네트워크들의 네트워크’라고 설명한다.

**자료 표현 주의:** 원문의 ‘모든 네트워크’는 세계의 모든 사설·폐쇄망이 예외 없이 인터넷에 접속한다는 뜻으로 읽지 않는다. 인터넷에 연결되지 않은 네트워크도 존재할 수 있다.

위성·지구 이미지와 도시의 연결선은 다양한 지역과 접속 방식을 통해 네트워크가 연결된다는 의미다. 모든 인터넷 통신이 위성을 반드시 거친다는 뜻은 아니다.

### 7.2 Network

**Network(네트워크)** 는 여러 시스템이 프로토콜을 통해 데이터를 주고받도록 연결된 집합이다.

자료는 ‘거대 결합체’라는 표현을 쓰지만, 네트워크가 성립하려면 반드시 매우 커야 하는 것은 아니다. 집 안이나 연구실의 작은 통신망도 네트워크다.

```text
집 안 네트워크 ─┐
학교 네트워크 ──┼── 서로 연결된 네트워크들 → Internet
회사 네트워크 ──┘
```

이는 개념도이며 각 네트워크가 아무 조건 없이 직접 연결된다는 뜻은 아니다.

### 7.3 Network·Internet·WWW를 함께 구분하기

Network는 일반적인 연결 집합, Internet은 서로 연결된 세계적인 네트워크 체계, WWW는 인터넷 기반의 서비스 체계다.

**보충 예시:** 외부 인터넷 접속이 끊겨도 집 안의 장치와 프린터 사이 통신은 가능한 경우가 있다. 로컬 네트워크의 동작과 인터넷 전체 접근 가능성은 같은 조건이 아니기 때문이다.

## 8. Node: 엔드 노드와 중계 노드

**자료: p.11**

자료의 Node 정의는 데이터를 주고받을 수 있도록 상호 연결된 시스템을 통칭한다는 것이다.

### 8.1 End Node / Host

**End Node(엔드 노드)** 또는 이 문맥의 **Host(호스트)** 는 데이터를 생성하거나 최종적으로 이용하는 통신의 끝점이다.

자료 그림의 예시는 모바일 기기, 노트북, 태블릿, 프린터, 서버 등이다. 서버도 네트워크 가장자리에서 서비스를 제공하는 끝점으로 볼 수 있으므로 ‘중요한 장비니까 중계 노드’라고 분류하지 않는다.

### 8.2 Intermediate Node

**Intermediate Node(중계 노드)** 는 다른 노드 사이의 데이터 전달을 돕는 역할을 한다. 그림에는 스위치, 라우터, 모뎀, 셀 타워 등이 중간 전달 요소로 표시된다.

**보충 설명:** 스위치와 라우터의 상세 동작은 후속 계층 학습에서 다루지만, 여기서는 최종 사용자 데이터를 이용하는 역할과 전달하는 역할을 구분하면 된다.

### 8.3 그림 두 개의 의미

왼쪽 그림은 다양한 엔드 장치가 중계 장비를 거쳐 연결되는 모습을 보여 준다. 오른쪽 그림은 여러 중계 노드가 망 형태로 연결되고 그 가장자리에 단말이 붙은 구조다.

이 그림들의 핵심은 **모든 엔드 노드가 서로 직접 케이블로 연결되어야 하는 것은 아니다** 라는 점이다. 중계 노드의 연결을 이용해 다른 끝점으로 데이터를 보낼 수 있다.

### 8.4 역할에 따른 분류라는 점

하나의 장비가 여러 역할을 가질 수 있다. 평소 중계하는 장비도 관리 기능을 위한 통신에서는 메시지를 생성하거나 받을 수 있다. 따라서 End/Intermediate 구분은 특정 통신에서 어떤 역할을 하는지에 초점을 둔다.

**System과 Node의 관계:** System은 기능을 수행하는 전체 구성을 설명하는 말이고, Node는 그 시스템을 네트워크 연결의 한 점으로 보는 말이다. 둘을 완전히 배타적인 사물 종류로 구분할 필요는 없다.

## 9. Gateway와 DNS

**자료: p.12**

### 9.1 Gateway — 다른 네트워크로 나가는 관문

**Gateway(게이트웨이)** 는 서로 다른 네트워크를 연결하거나 그 경계를 통과하는 통신을 돕는 관문 역할을 한다.

**자료 표현 주의:** Gateway 아래의 정의 문장은 직전 Node 정의와 동일하게 반복되어 있다. 이를 Gateway의 정확한 정의로 외우면 모든 노드가 Gateway가 되는 오류가 생긴다. 그림이 보여 주는 **서로 다른 네트워크 사이의 연결 역할** 을 중심으로 이해한다.

그림에는 왼쪽과 오른쪽 장치 그룹이 있고, 위쪽의 연결 장비가 `GATEWAY`로 강조되어 있다. 같은 그룹 내부의 전달과 다른 그룹으로 나가는 전달을 구분하라는 뜻이다.

### 9.2 Default Gateway의 간단한 예

**보충 설명:** 호스트가 목적지가 자신의 로컬 네트워크 밖에 있다고 판단하고 더 구체적인 경로가 없을 때, 기본적으로 다음 전달을 맡기는 라우터를 Default Gateway라고 부른다.

```text
내 PC → 로컬 네트워크의 기본 Gateway → 다른 네트워크 → 목적지
```

Gateway는 맥락에 따라 서로 다른 프로토콜이나 서비스 사이를 연결·변환하는 더 넓은 의미로도 쓰인다. 따라서 모든 Gateway가 언제나 동일한 종류의 변환을 수행한다고 외우지 않는다. 이 장의 그림에서는 우선 네트워크 사이의 관문 역할에 집중한다.

### 9.3 DNS — 이름과 주소를 연결하는 서비스

**DNS(Domain Name System)** 는 사람이 읽기 쉬운 도메인 이름과 IP 주소 등 관련 정보를 연결하는 이름 시스템이다. 자료에서는 ‘네트워크의 전화번호부’라는 비유를 사용한다.

**자료의 핵심:** 사람은 이름으로 대상을 기억하기 쉽지만, IP 통신에는 주소 정보가 필요하다. DNS는 그 둘을 연결한다.

### 9.4 DNS 요청·응답 그림 읽기

p.12 오른쪽 그림은 Client System이 DNS Server에 질의하고 응답받는 구조다. 요청에는 이름과 질의 종류가, 응답에는 결과가 표시되어 있다.

```text
클라이언트                       DNS 서버
    │                               │
    ├── 이름에 대한 주소 질의 ──────→│
    │←──── 주소 등 조회 결과 ────────┤
    │                               │
    └── 얻은 주소로 목적지 서비스와 통신
```

마지막 줄은 그림의 의미를 연결한 보충이다. DNS 서버가 웹 콘텐츠 자체를 반드시 제공하는 것은 아니다. **주소를 알아내는 일과 그 주소의 서버에서 콘텐츠를 받는 일** 은 구분한다.

그림에 보이는 `Type A`는 IPv4 주소 레코드 질의와 관련된다. DNS는 이 기능 외에도 다른 종류의 정보를 다룰 수 있지만, 이 장에서는 이름과 주소의 연결을 중심으로 학습한다. DNS 계층 구조·캐시·세부 레코드 체계는 후속 수업 범위로 남긴다.

### 9.5 자료의 8.8.8.8 예시를 읽을 때 주의

원문에는 `www.google.com`을 `8.8.8.8`로 변환한다는 형태의 예시가 있다. 이는 이름과 주소라는 개념을 보여 주려는 예로 보이지만, 실제 대응으로 암기하면 안 된다.

**8.8.8.8은 Google Public DNS 서버 주소** 이다. 즉 DNS 질의를 보내는 서버의 주소와 조회 결과로 받는 웹 서버 주소를 구분해야 한다. [Google Public DNS 공식 안내](https://developers.google.com/speed/public-dns)

학습 예시는 다음처럼 읽는 것이 안전하다.

```text
조회할 대상: 어떤 웹사이트의 도메인 이름
질의를 받는 곳: 설정된 DNS 서버
응답 결과: 해당 이름에 대응하는 주소 정보
```

### 9.6 Gateway와 DNS의 차이

- Gateway: 데이터를 **다른 네트워크로 전달하는 관문**.
- DNS: 이름에 대응하는 **주소 정보를 알아내는 서비스**.

집의 공유기 한 대가 두 기능을 함께 제공하거나 중계할 수 있어도 개념은 다르다. 이름 해석 실패와 외부 네트워크 전달 실패도 구분해야 한다.

### Q2. ARPANET이 처음 만들어진 결정적인 이유는?

1. 전 세계 사람들이 유튜브를 보게 하려고.
2. 온라인 쇼핑을 안전하게 하기 위해.
3. 핵전쟁 같은 비상시에도 통신이 끊기지 않게 하려고.
4. 대학생들의 수강신청을 돕기 위해.

**보기 구성상 의도된 답으로 추정되는 항목: ③. 공식 정답 표시는 자료에 없다.**

다른 보기들은 ARPANET의 개발 목적을 설명하지 못한다. 다만 ③을 역사적 사실의 정확한 요약으로 단정해서는 안 된다.

**역사적 보충:** Internet Society의 인터넷 역사 설명은 ARPANET과 인터넷의 중요한 초기 동기로 컴퓨팅 자원 공유를 제시하며, ARPANET이 핵전쟁 생존을 위해 시작되었다는 통념을 구분한다. 분산 통신의 군사적 생존성 연구와 ARPANET의 개발 목적을 하나로 합치지 않는 것이 정확하다. [Internet Society, A Brief History of the Internet](https://www.internetsociety.org/internet/history-internet/brief-history-internet/)

**학습 답안:** “강의 보기상 ③을 의도한 것으로 보이나, ARPANET의 주요 개발 동기는 연구용 컴퓨팅 자원 공유였으며 핵전쟁 대비만을 결정적 이유로 설명하는 것은 부정확하다.” 이 구분을 기억하고 실제 채점 기준은 수업 설명과 함께 확인한다.

### Q3. Protocol을 일상에 비유하면 가장 가까운 것은?

1. 고속도로의 제한 속도.
2. 대화를 나누기 위한 공통된 언어.
3. 최신형 스마트폰 기계.
4. 데이터를 저장하는 USB 메모리.

**정답: ② 공통된 언어.**

Protocol은 교환 내용을 서로 이해하고 정해진 방식으로 반응하게 하는 약속이다. 기계 자체인 ③이나 저장 장치인 ④보다 ②가 적절하다. ①도 규칙이라는 속성은 있지만, 상호 메시지 교환을 나타내는 비유로는 ②가 더 가깝다.

**심화 확인:** 프로토콜은 언어의 단어뿐 아니라 메시지 형식·의미·교환 절차까지 포함할 수 있다.

### Q4. 인터넷의 주인은 누구인가?

1. 미국 정부.
2. 구글과 애플 같은 거대 IT 기업.
3. 국제 인터넷 주소 기구(IANA)로 제시된 항목.
4. 단일 주인 없이 모두가 연결된 거대한 자율적 네트워크.

**정답: ④.**

인터넷 전체를 한 기관이나 기업이 단독으로 소유하는 구조는 아니다. 여러 조직이 운영하는 네트워크가 연결되어 동작한다.

**헷갈림 방지:** ‘전체의 단일 주인이 없다’는 말은 개별 회선·서버·라우터의 소유자가 없거나 관리 규칙이 없다는 뜻이 아니다. 각 자원과 네트워크에는 운영 주체가 있다.

IANA는 Internet Assigned Numbers Authority의 약자다. 인터넷의 번호·식별자 관련 조정 기능과 인터넷 전체의 소유권을 혼동하지 않는다. 표준화 기구 역시 인터넷 전체를 소유하는 기관은 아니다.

### Q5. 인터넷 역사상 최초로 전송된 메시지는?

1. HELLO.
2. LOGIN.
3. LO.
4. GOOGLE.
5. WWW.

**정답: ③ LO.**

정확히는 초기 ARPANET의 첫 호스트 간 메시지에 관한 질문이다. `LOGIN`을 보내려 했지만 중간에 시스템 문제가 발생해 처음 전달된 부분은 `LO`였다. UCLA의 기록도 이 구분을 설명한다. [UCLA, 인터넷 50주년 기록](https://newsroom.ucla.edu/releases/internet-50-symposium-ucla)

**출제 포인트:** 보내려던 메시지와 처음 실제 전달된 메시지를 구분한다.

```text
의도: LOGIN
처음 전달된 부분: LO
```

### Q6. 인터넷이 안 될 때 ping은 어떤 프로토콜의 도움을 받는가?

**정답: ICMP(Internet Control Message Protocol).**

일반적인 IPv4 ping은 ICMP Echo Request를 보내고 Echo Reply 응답을 이용한다. ICMP의 Echo와 Echo Reply는 RFC 792에 정의되어 있다. [RFC 792: ICMP](https://www.rfc-editor.org/info/rfc792/)

```text
내 호스트 ── ICMP Echo Request ──→ 대상
내 호스트 ←─ ICMP Echo Reply ───── 대상
```

**보충 설명:** IPv6에서는 ICMPv6를 사용한다. 이 문제의 기본 답은 ICMP다. ping은 응용 프로그램 이름이며 그 요청이 TCP 또는 UDP Port를 사용한다고 설명하면 안 된다.

**진단의 한계:** 응답이 있으면 해당 대상과 해당 방식의 통신이 가능하다는 근거가 된다. 그러나 웹 서비스 정상 동작까지 보장하지는 않는다. 반대로 응답이 없다고 항상 인터넷 전체가 끊겼다고 단정할 수는 없다. 대상 또는 중간 장비가 해당 요청에 응답하지 않도록 설정되어 있을 수도 있다.

### Review 정답 빠른 확인

```text
Q1: ② — 정보는 Node가 아니다.
Q2: ③이 보기상 의도된 답으로 추정됨 — 역사적 설명은 주의.
Q3: ② — 공통 대화 규칙.
Q4: ④ — 인터넷 전체의 단일 소유자는 없음.
Q5: ③ — LO, 의도한 메시지는 LOGIN.
Q6: ICMP — Echo Request / Echo Reply.
```

## 11. 통합 예시와 헷갈리기 쉬운 포인트

### 11.1 노트북으로 외부 웹 서비스를 이용하는 상황

**보충 예시 — 이 장의 용어를 연결하는 학습용 시나리오**

1. **System:** 노트북의 하드웨어, 운영체제, 응용 프로그램, 통신 기능이 함께 동작한다.
2. **Node:** 노트북은 요청을 만드는 End Node다.
3. **Interface:** 프로그램은 Socket/API 같은 논리적 접점을 이용하고, 장치는 네트워크 연결을 위한 인터페이스를 이용한다.
4. **Transmission Media:** 유선이면 케이블, 무선이면 공간을 통해 신호가 전달된다.
5. **Protocol:** 각 계층에서 공통 메시지·전송 규칙을 따른다.
6. **Standardization / Interoperability:** 다른 제조사의 장비와 운영체제가 공통 규격을 구현해 함께 통신한다.
7. **Network:** 노트북이 속한 로컬 통신망이 있다.
8. **Gateway:** 외부 목적지로 나가는 전달을 맡는 관문을 이용한다.
9. **DNS:** 필요한 경우 이름에 대응하는 주소 정보를 조회한다.
10. **Internet:** 여러 네트워크를 거쳐 상대 End Node인 서버와 통신한다.

위 번호는 **용어를 연결하는 설명 순서** 다. 실제 실행 순서를 그대로 뜻하지 않는다. 예를 들어 DNS 조회 자체도 게이트웨이를 거쳐 외부 DNS 서버로 전달될 수 있고, 이미 얻은 주소 정보를 사용할 수도 있다.

### 11.2 물리적으로 맞으면 통신도 되는가?

아니다. 물리적 접점이 맞는 것, 신호를 주고받는 것, 프로토콜이 맞는 것, 응용이 내용을 해석하는 것은 서로 다른 조건이다. 앞 단계가 된다고 뒤 단계가 자동으로 성공하지 않는다.

### 11.3 표준화와 상호 운용성은 같은 말인가?

표준화는 공통 규격을 정하고 맞추는 과정이고, 상호 운용성은 실제로 함께 동작할 수 있는 성질이다. 둘은 원인과 목표의 관계로 연결되지만 동의어는 아니다.

### 11.4 Gateway와 DNS는 같은 장비인가?

같은 기기에서 관련 기능을 제공할 수는 있지만 개념은 다르다. Gateway는 네트워크 간 전달 관문, DNS는 이름 정보 조회 체계다.

### 11.5 모든 Node는 Host인가?

이 장의 분류에서는 아니다. Node에는 End Node와 Intermediate Node가 있다. 통신 끝점인 Host뿐 아니라 중계 역할의 장치도 Node에 포함된다.

### 11.6 인터넷의 단일 소유자가 없으면 표준도 없는가?

아니다. 운영 주체가 여러 곳이어도 공통 규격과 조정 기능은 필요하다. 오히려 서로 다른 운영 주체가 연결되므로 표준화와 상호 운용성이 중요하다.

## 12. 시험 대비 핵심과 자체 점검

### 12.1 짧게 정의할 용어

- **Interface:** 연결·기능 이용을 위한 접점과 이용 방식.
- **Protocol:** 데이터 교환의 형식·의미·절차에 관한 규칙.
- **Standardization:** 서로 연동하도록 공통 규격을 정하는 과정.
- **Interoperability:** 서로 다른 시스템이 정보를 교환하고 활용해 함께 동작하는 성질.
- **System:** 하드웨어·소프트웨어 등 기능을 수행하는 전체 구성.
- **Transmission Media:** 신호가 실제 전달되는 매체나 경로.
- **Network:** 데이터를 교환하도록 연결된 시스템들의 집합.
- **Internet:** 여러 네트워크가 연결된 세계적인 네트워크 체계.
- **Node:** 네트워크에 연결된 통신 주체 또는 중계 시스템.
- **Gateway:** 네트워크 사이의 관문 역할.
- **DNS:** 이름을 IP 주소 등 관련 정보와 연결하는 시스템.

### 12.2 서술형 답안 연습

**문제 1. Interface·Protocol·Standardization을 Interoperability와 연결하여 설명하라.**

**답안 예시:** 인터페이스는 시스템이 연결되거나 기능을 이용하는 접점을 제공하고, 프로토콜은 그 연결에서 데이터를 교환하는 규칙을 정한다. 표준화는 서로 다른 시스템이 공통 규격을 따르도록 한다. 이를 올바르게 구현하면 제조사나 운영체제가 달라도 정보를 교환하고 함께 동작하는 상호 운용성을 확보할 수 있다.

**문제 2. 전송 매체와 프로토콜의 차이를 송신자·수신자 그림으로 설명하라.**

**답안 예시:** 전송 매체는 송신자에서 수신자로 신호가 이동하는 통로다. 프로토콜은 송신자가 보낸 메시지의 형식과 의미를 수신자가 이해하고 정해진 방식으로 응답하도록 하는 규칙이다. 통로만 있다고 의미 있는 교환이 성립하지는 않는다.

**문제 3. 같은 장비가 Gateway 기능과 DNS 관련 기능을 제공해도 둘을 구분해야 하는 이유는?**

**답안 예시:** 장비가 같아도 해결하는 문제가 다르기 때문이다. Gateway는 다른 네트워크로 전달하는 문제를, DNS는 이름에 대응하는 주소 정보를 얻는 문제를 다룬다.

**② ISO와 OSI는 동일한 대상을 가리키는 약자다.**

## 13. 장 마지막 총정리

3장의 핵심은 **연결되어 있다는 사실만으로 통신이 완성되는 것은 아니다** 라는 점이다.

시스템은 인터페이스를 통해 연결을 이용하고, 전송 매체를 통해 신호를 전달하며, 프로토콜에 따라 정보를 교환한다. 서로 다른 구현이 공통 규격을 따르도록 하는 표준화는 상호 운용성의 중요한 기반이다.

이런 시스템을 연결의 관점에서 보면 Node가 되고, 노드들이 데이터를 교환하는 집합은 Network가 된다. 여러 네트워크가 연결되어 Internet을 구성하며, 다른 네트워크로 나가는 과정에는 Gateway, 이름과 주소 정보를 연결하는 과정에는 DNS가 관련된다.

```text
System
  ├─ Interface로 접점 이용
  ├─ Transmission Media로 신호 전달
  └─ Protocol로 정보 교환
          ↑
   Standardization으로 공통 규격
          ↓
   Interoperability 확보

연결된 System → Node
Node들의 통신 집합 → Network
Network들의 상호 연결 → Internet
다른 Network로 나가는 관문 → Gateway
이름과 주소 정보 연결 → DNS
```

1장이 학습의 큰 지도를, 2장이 계층별 데이터 흐름을, 3장이 상호 연결의 조건과 용어를 제공했다. 다음 Network Access Layer 학습에서는 이 기반 위에서 **실제 링크에서 프레임과 신호가 어떻게 전달되는가** 를 구체적으로 살펴보게 된다.
